# realtime-asr

本文是产品目标、目标用户、核心工作流程、建设范围和非目标的权威依据。

realtime-asr 是独立的实时自动语音识别（Automatic Speech Recognition，ASR）项目。用户可以单独运行项目，也可以将识别能力接入其他程序。

本文描述已确认的目标产品，不表示功能已经实现。系统组织见[架构文档](ARCHITECTURE.md)，能力建设顺序见[项目规划](ROADMAP.md)，实际进展与验证范围见[开发状态](STATUS.md)。

## 问题

用户需要将持续输入的语音转换为文本。说话期间，用户需要看到当前识别文本；语音结束后，用户需要获得完整的最终文本。短暂停顿、连续说话和较慢的最终推理，都可能造成误切句、漏音频或结果归属混乱。

单独使用时，项目负责采集麦克风。接入其他程序时，调用方提供音频。两种用法需要共用识别、分句、候选结果和生命周期能力，避免调用方重新实现这些规则。

使用者还需要知道识别结果的来源与可信范围。可变实时文本、稳定前缀、候选文本和最终文本具有不同含义。将这些文本混成一种结果，会使调用程序过早采用未完成的识别假设。

服务使用者需要在多个连接共享模型时保持音频和结果隔离。模型尚未就绪、输入积压或客户端接收缓慢时，服务应给出明确状态，不能以静默丢弃音频维持表面上的实时输出。

## 目标用户

### 单独使用的用户

用户在本机启动命令行工具，选择麦克风并持续说话。用户查看实时文本、各段最终文本和错误信息，也能识别已有音频文件。

浏览器使用界面提供麦克风采集、结果展示和运行状态查看。浏览器通过识别服务使用同一套识别能力，不形成另一套产品规则。

### 接入其他程序的开发者

开发者把其他程序采集或接收的音频交给项目，读取实时、候选和最终结果。开发者也需要控制开始、结束、取消、重置和关闭，并判断结果属于哪个会话、录音段或整轮音频。

Python 程序直接调用 Python SDK。SDK 指供程序调用的公开接口。跨进程、跨语言或跨机器的程序通过 HTTP 或 WebSocket 接入，也可使用配套 Python 远程客户端。

### 启动识别服务的使用者

使用者选择模型、设备和容量配置，启动服务并向调用方提供地址。使用者需要判断模型是否就绪、服务能否接受任务，以及排队和推理分别花费多少时间。

使用者需要可复现的安装与模型准备方式。干净环境、CPU／GPU 配置和离线模型使用，应有明确的支持边界。

## 产品原则

### 两种音频用法，共用识别能力

产品提供两种音频用法：使用麦克风；接收外部音频。SDK、HTTP 和 WebSocket 是接入方式，不增加第三种音频来源。

命令行、SDK、远程客户端和浏览器共用识别规则。入口可以选择不同的使用模式，但不能改变结果的含义。

### 音频完整性优先

在确认的配置和容量内，识别上一段时应继续接收后续音频。刷新、分句和结束时应保留已接受的有效样本，避免漏掉句首、句尾或下一句。

达到容量限制时，系统应明确拒绝、降级或结束。可替换的实时快照可以合并；最终识别需要的原始音频不能静默丢弃。

### 结果来源明确

实时文本是当前识别假设，可以变化。稳定前缀表示实时链路已提交的显示部分，但不保证与最终识别完全相同。

候选文本是尚未结束时的一次识别结果。最终文本是结束操作或自动分句确认后的完成结果。输出应说明来源及适用音频范围，调用方能判断是否需要替换旧文本。

### 独立安装与按需依赖

项目应从自身安装包运行。只使用外部音频的程序，不应被迫安装麦克风采集、浏览器或所有模型运行时。

引擎扩展能力不等于引擎数量承诺。正式接通实现已确认能力所需的引擎，不以移植全部适配器为目标。

### 失败与完成可区分

模型加载失败、音频无效、设备失败、推理失败、超时、取消和容量不足，应产生可判断的结果。没有识别到语音与识别失败应有不同含义。

结束、取消或重置后，旧任务不能继续覆盖新状态。关闭时应说明尚未完成的工作如何结束，并释放设备及会话资源。

### 验证项与交付项分开

验证用于判断某个候选是否值得接入。只验证的引擎不进入正式交付清单，不因为试跑成功就自动转为受支持后端。

范围变更应先更新本文，再同步架构和规划。开发任务、实验结果和扩展接口不能自行扩大产品范围。

## 核心工作流程

以下流程描述目标行为。当前实现情况见“当前能力”。

### 使用麦克风连续识别

1. 用户启动本地命令行工具，选择运行配置和麦克风。
2. 系统准备模型和采集设备，报告就绪或失败状态。
3. 用户持续说话，系统检测开口并保留句首音频。
4. 系统输出可变实时文本，也可展示稳定前缀。
5. 系统确认一句结束，输出该录音段的最终文本。
6. 最终识别期间，系统继续接收下一句音频。
7. 用户停止使用，系统按关闭规则结束任务并释放设备。

用户可以启用唤醒词后再开始识别。唤醒后的等待、超时和继续说话窗口，应让用户知道当前能否直接说正文。

### 程序提供持续音频

1. 调用方创建 SDK 会话或连接识别服务。
2. 调用方选择自动分句或手动结束模式。
3. 调用方按声明格式送入音频，系统报告是否接受。
4. 调用方接收实时结果和对应的音频归属信息。
5. 自动分句确认边界，或调用方发出结束操作。
6. 调用方获得最终结果及完成状态。
7. 调用方继续下一段音频，或关闭会话。

自动分句模式可以连续产生多个录音段。手动模式由调用方控制整轮音频结束，不能把内部短暂停顿当成调用方已经完成。

调用方可以取消当前工作或重置会话。系统应阻止已失效任务继续发布结果。

### 识别完整音频

用户通过命令行提交音频文件，或调用方通过 SDK／HTTP 提交整段音频。系统返回最终文本、可用的识别信息或明确失败。

已有文件也可以按实时节奏送入，用于复现连续识别和分句问题。整段识别不要求产生实时文本；模拟实时输入应遵守持续会话规则。

### 在结束前请求候选文本

调用方可以请求尾部修复候选，或整轮候选。两者的文本来源和覆盖范围应能区分。

尾部修复候选用于改善当前实时文本的末尾。无法可靠对齐时，系统报告修复状态，不能把尾部输出伪称为完整整轮识别。

整轮候选根据请求时保留的完整音频生成。此结果不使用实时文本代替音频输入。候选请求可以异步执行，持续输入不等待候选完成。

调用方确认候选边界后，可以在同一轮音频中继续说话。系统保留此前音频，并区分恢复前后候选的归属。此能力称为同轮继续（Resume），不表示断线后恢复历史会话。

### 使用候选与最终结果的不同策略

系统提供提示性提前候选、仅使用候选引擎完成识别，以及显式请求延后整轮修正的运行策略。

候选仍对应当前音频版本时，结束操作可以复用它。接受了新音频后，系统应重新生成需要覆盖新音频的结果。延后修正应关联此前结果，让调用方明确替换关系。

### 使用浏览器与共享服务

用户连接浏览器界面并授权麦克风，开始、停止或清除当前展示。界面展示实时文本、最终文本、候选来源及状态，并允许复制识别文本。

服务使用者查看模型就绪、会话容量、队列与推理耗时。多个调用方共享模型，但不能共享录音状态或收到彼此的识别文本。

## 当前能力

项目已建立 P0 本地验证入口，接通 Whisper 整段、周期快照和 Nemotron 原生流式路径。当前真实试跑使用公开语料标注草稿；语料听音及正式阶段验收仍未完成。

本文中的麦克风、SDK、服务、实时文本稳定、候选、同轮继续和唤醒能力，均属于已确认的待交付范围。P0 的模型运行与测量记录不能替代这些产品能力的验收，也不构成正式质量或运行容量承诺。

文档已明确目标与取舍，不构成实现完成或验收通过的证据。实际进展由[开发状态](STATUS.md)记录。

### 识别后端与验证环境

正式建设需要普通整段识别及原生流式识别的可用后端。基线阶段先验证最终识别候选和流式候选，再确定正式适配器与模型配置。高级候选或双实时识别需要额外后端时，也应说明具体需求并完成验证。

faster-whisper 是普通识别基线候选，Sherpa Nemotron 是原生流式候选。Kroko 当前暂不接入，不进入基线验证或默认后续任务。其他非排除后端只在已确认能力确有需要时评估，不承诺全部接通。

Windows 本地运行优先验证，语言评估以中文为主，英文补充。CPU、GPU、平台和模型支持应以实际验证组合说明，不以某个后端支持某平台推导所有后端都支持。

效果、延迟和容量门槛由运行基线及对应功能规格确认。此处不编造性能数值，也不将候选名称视为正式支持声明。

## 成功标准

### 独立使用与可安装性

用户能在确认的环境中，从干净安装开始运行命令行工具。用户能选择麦克风、连续识别多句、识别已有文件，并看见明确状态与结果。

停止后设备能再次使用。预下载模型后，确认支持的识别流程能离线运行。所需依赖、模型和设备配置能被另一个使用者复现。

### 程序接入与结果含义

独立 Python 程序能安装 SDK、提交音频、结束或取消识别，并消费对应结果。HTTP 与 WebSocket 客户端能完成各自使用流程。

调用方能区分可变实时文本、稳定前缀、两种候选、最终文本和终结状态。不同入口对同一模式使用一致的结果含义。

### 音频完整性与连续识别

确认容量内，慢最终推理不会造成下一句音频丢失。尾部刷新不漏掉不足一块的音频，前置缓冲和分句不剪掉正文首词。

切分、恢复和整轮候选都能说明实际覆盖范围。已结束录音与继续输入的音频不会相互改写。

### 实时质量与高级结果

两种实时路径均有实际运行验证。稳定文本、声学触发、提前推理和动态等待，应有相同语料的效果与成本记录。

双实时模型在缺少可信锚点时不拼接未经确认的尾部。最终识别仍以对应音频为依据，能修正实时结果。

尾部候选能报告对齐失败。整轮候选确实覆盖完整保留音频，不以实时文本替代模型输入。候选失效、复用与延后修正有可检查依据。

同轮继续保留此前音频，并阻止恢复前旧候选覆盖恢复后的状态。继续应答和后续结果顺序清楚，不使客户端误认候选归属。

### 唤醒与使用界面

两种唤醒后端在各自确认的环境中，完成触发、超时和正文识别验证。唤醒音频裁剪不丢正文首词；后续窗口到期后恢复正确门控。

浏览器能实际采集音频并展示对应文本、状态和时间线。复制、清除与停止不会改变后台识别结果的含义。

### 共享服务与失败处理

多个真实会话互不串音或串结果。公平调度、慢客户端、超额输入、模型失败、取消、重置和断开均有明确处理结果。

输入、任务和输出队列有可查询或可记录的上限。最终与完成事件的顺序受保护，服务不以无限积压隐藏容量问题。

### 识别效果、性能与范围一致性

验收记录说明硬件、模型、语言、语料和测量方法。首个实时结果、结束后最终等待、识别错误率和资源使用分别记录。

自动化行为验证、真实模型验证和真实设备使用分别提供证据。模型加载成功、模拟测试通过或单段转写成功，都不能代替完整产品验收。

Qwen 与 FunASR 的验证结论不计为正式交付。非目标中的能力不能出现在安装包、能力查询或使用说明中被宣称为已支持。
