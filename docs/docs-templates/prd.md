# PRD：产品需求文档的编写与维护

本文说明产品需求文档（PRD）的用途、应包含的内容、与其他文档的分工，以及使用和维护规则。创建或更新项目的 PRD 时，可按本文确定内容范围和组织结构；开发过程中，可按本文判断如何查阅和同步 PRD。

## PRD 是什么

PRD（Product Requirements Document，产品需求文档）是项目的权威产品文档。它回答：我们要构建什么产品，为谁构建，以及为什么构建。

PRD 描述整个产品，不描述单个功能的详细实现。通过 PRD 理解产品目标、用户需求、产品范围和非目标，并判断当前请求是否属于产品范围。

## 文件与权威入口

默认将 PRD 保存在 `docs/PRD.md`。一个产品通常只维护一份主 PRD，不应在没有实际需要时创建多份相互竞争的 PRD。

PRD 应在开头明确自身职责。例如：

> 本文是产品范围、目标用户、核心工作流程和非目标的权威依据。

不要过早拆分 PRD。只有当文档难以导航时，才将详细内容拆入多个文件。拆分后，`docs/PRD.md` 仍是主入口，并链接详细文档。多个文件共同维护一份逻辑上的产品约定。

## PRD 应写什么

以下是推荐内容，用于说明整个产品。

| 内容 | 应回答的问题 | 填写边界 |
| --- | --- | --- |
| 产品名称 | 这是什么产品？ | 使用产品名称作为文档标题。 |
| 问题 | 产品解决什么问题？ | 说明用户遇到的困难，以及产品希望带来的结果。 |
| 目标用户 | 谁在什么情境下需要产品？ | 说明用户和使用场景，避免只写“所有人”或“个人用户”。 |
| 产品原则 | 哪些原则指导产品决策？ | 写能够指导取舍的原则，避免“体验好”等无法指导决策的口号。 |
| 核心工作流程 | 用户如何完成主要活动？ | 说明起点、主要活动和最终结果，不展开全部交互状态。 |
| 当前能力 | 产品目前已经具备哪些能力？ | 概述已具备的能力，不写待实现需求或详细验收记录。 |
| 当前范围 | 当前版本或阶段承诺交付什么？ | 说明产品边界，不写任务清单、执行顺序或开发进度。 |
| 非目标 | 哪些内容明确不做？ | 说明排除项适用于当前版本、阶段，还是产品长期边界。 |
| 成功标准 | 什么结果表示产品或版本取得成功？ | 说明用户能够完成什么，以及原有问题如何得到解决。 |

“当前范围”可以同时包含已具备和待交付的能力；“当前能力”只记录已具备的部分。新项目尚未交付能力时，可直接注明“尚未交付”。核心工作流程应说明描述的是已有流程还是目标流程，避免将目标写成已实现的事实。

成功标准应能通过用户操作、结果检查或评估来判断。需要指标时，应根据产品目标确定评估方法和阈值，不应为了填满模板而编造数值。具体功能的验收场景由 Spec 维护。

推荐结构如下：

```markdown
# <产品名称>

本文是产品范围、目标用户、核心工作流程和非目标的权威依据。

## 问题

## 目标用户

## 产品原则

## 核心工作流程

## 当前能力

## 当前范围

## 非目标

## 成功标准
```

### 参考示例：个人笔记产品

以下示例展示各部分的写法。产品能力、范围和成功标准均为示例，不构成其他项目的需求。

```markdown
# 个人笔记

本文是产品范围、目标用户、核心工作流程和非目标的权威依据。

## 问题

个人学习和工作中的信息分散，记录后难以再次找到。
较长的笔记需要反复阅读，才能回顾主要内容。

产品帮助用户集中记录信息、查找已有笔记，并通过摘要回顾内容。

## 目标用户

- 需要记录和回顾学习资料的个人用户。
- 需要保存工作笔记，并按关键词查找内容的个人用户。

## 产品原则

- 优先保证记录、编辑和查找笔记的基本流程。
- 用户保留对笔记正文的控制，AI 摘要不自动替换正文。
- AI 摘要失败时，用户仍能阅读和编辑笔记。

## 核心工作流程

以下是当前版本的目标流程，已具备的能力见“当前能力”。

### 记录与修改笔记

用户创建笔记，填写标题和正文并保存。
用户之后可以重新打开笔记，修改内容并再次保存。

### 查找已有笔记

用户输入关键词，查看匹配的笔记，并打开需要的内容。
没有匹配结果时，用户可以修改关键词后重新搜索。

### 回顾长笔记

用户打开一篇笔记，主动请求生成 AI 摘要。
用户阅读摘要，必要时对照原文查看细节。
摘要生成失败时，用户可以继续阅读原文或重新发起请求。

## 当前能力

- 创建、编辑、保存和阅读笔记。
- 按关键词搜索笔记。

AI 摘要尚未交付。

## 当前范围

当前版本覆盖个人笔记的记录、编辑、搜索和单篇 AI 摘要。
用户通过这些能力保存信息、重新找到笔记，并回顾长笔记的主要内容。
摘要由用户主动触发，不自动修改笔记正文。

## 非目标

当前版本不提供以下能力：

- 团队协作。
- 嵌套文件夹。
- 知识图谱。
- 公共市场。

## 成功标准

- 用户能够完成创建、保存、重新打开和修改笔记的完整流程。
- 用户能够通过关键词找到已保存的目标笔记。
- 用户能够通过单篇摘要识别笔记的主要内容，并回到原文核对。
- 摘要生成失败不会造成正文丢失，也不会阻止继续编辑。
```

## PRD 不应写什么

PRD 不应包含以下详细实现信息：

- 数据库表结构。
- API 响应结构。
- React 组件名称。
- 类结构。
- Repository 接口。
- 数据迁移细节。
- 函数签名。

这些内容应根据职责归入架构文档、Spec 或代码。不要在 PRD 中重复代码已经直接表达的实现细节。

## 与其他文档的分工

PRD 维护产品范围。其他文档分别维护系统结构、功能行为、决策理由和当前执行范围。相同信息不应在多个文档中重复维护。

| 文档 | 负责的内容 | 公开分享笔记的示例 |
| --- | --- | --- |
| PRD | 产品目标与范围 | 用户可以公开分享笔记。 |
| Architecture | 系统级结构规则 | 公开访问使用独立的分享令牌机制，不复用私有笔记接口。 |
| Spec | 具体功能行为 | 用户可以生成和撤销只读链接；撤销后访问返回 404。 |
| Decision | 重要决策的理由 | 使用随机分享令牌，避免暴露内部资源标识。 |
| Plan（实施计划） | 当前实施范围 | 实现公开分享，不增加评论或协作。 |
| Status（开发状态） | 当前进展、验收情况和后续安排 | 分享功能实现完成，自动化验证通过，用户试用待完成。 |

PRD 可以概述产品能力，具体功能行为由 Spec 说明。Plan 安排实施任务，Status 记录执行状态和验收结果。PRD 不应复制详细行为规则、任务清单或进度记录。

## 如何使用 PRD

对于非简单工作，应先读取 PRD，理解产品目标、用户需求、范围和非目标，再确认请求是否属于产品。

不应在实现时自行增加产品需求。例如，用户要求增加笔记标签，不代表同时要求标签颜色、嵌套标签、AI 打标、标签统计或标签权限。

应使用 PRD 理解产品意图，使用代码了解当前实现。现有代码可能包含缺陷、临时方案、过时行为或未经确认的假设，不能自动成为产品要求。

当 PRD 与代码冲突时，应核实原因：代码有误、文档过时，或迁移尚未完成。不应默默选择其中一方。

Plan 不应悄悄重新定义产品范围。例如，PRD 已排除团队协作，而 Plan 要求为未来团队协作增加 `workspace_id`，这属于产品范围冲突，应先解决冲突再实施。

## 何时维护 PRD

当产品范围、产品约定或已交付能力变化时，更新 PRD 中对应的内容。不要因为每次小规模代码修改而重写 PRD。

| 变化 | PRD 的维护方式 |
| --- | --- |
| 将登录按钮文字从“Login”改为“Sign in” | 通常不需要更新。 |
| 确认将公开分享笔记纳入当前版本 | 更新当前范围和核心工作流程，不提前写入当前能力。 |
| 公开分享笔记功能交付 | 根据实际交付结果更新当前能力，即使产品范围没有变化。 |
| 增加团队工作区 | 需要较大的产品范围更新。 |
| 当前版本或阶段切换 | 核对当前范围、非目标和成功标准，更新发生变化的内容。 |
| 调整内部实现，但产品约定不变 | 不需要因此更新 PRD。 |

只有部分能力交付时，应说明当前能力的边界，不应把完整目标写成已经具备。详细验收结果仍由 Status 维护。

功能请求到来时，应先判断是否改变产品行为和范围，再更新受影响的文档。不要要求每次小改动都修改 PRD、架构文档、Spec 和决策记录。

PRD 是长期维护的产品依据。文档的详细程度应与需求歧义、风险和长期影响相称，使局部开发工作符合产品目标。
