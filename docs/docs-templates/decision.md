# Decision：决策记录的编写与维护

本文说明决策记录（Decision）的用途、记录条件、应包含的内容，以及使用和维护方式。需要保留重要产品或技术选择的理由时，可按本文确定记录范围，并参考模板和示例组织文档。

## Decision 是什么

Decision 记录重要产品或技术决策及其理由。它回答：当时遇到了什么问题，选择了什么，为什么这样选择，以及接受了哪些代价。

代码和设计文档通常能够说明采用了什么方案，但未必能说明为什么采用。Decision 保存这些容易遗失在讨论或聊天中的理由，帮助后续维护者理解已有选择。

Decision 是决策理由的记录，不是完整技术设计，也不承担实施任务或进度记录的职责。

## 什么时候需要 Decision

当一项重要选择的理由无法从最终代码或当前设计中直接理解，且后续维护仍需要这些理由时，应记录 Decision。

典型问题包括：

- 为什么选择某种数据库或身份认证服务？
- 为什么使用轮询而不是 WebSocket？
- 为什么在保存前校验 AI 输出？
- 为什么选择软删除而不是直接删除？

不需要为每次局部代码选择创建记录。是否创建取决于决策的重要性和理由的保留价值，不取决于修改了多少文件。

## 文件与职责范围

默认将决策记录保存在 `docs/decisions/<decision>.md`。通常一项重要决策对应一份记录，文件名应能识别决策主题。

记录应围绕一个具体选择，保持简短。产品目标、系统结构和功能行为分别由 PRD、Architecture 和 Spec 维护；Decision 说明形成这些约定的原因。

## Decision 应写什么

| 内容 | 应回答的问题 | 填写边界 |
| --- | --- | --- |
| 背景 | 什么问题或取舍要求作出决定？ | 说明当时的需求和约束，不复制完整讨论过程。 |
| 决策 | 选择了什么？ | 写清采用的方案，不只写“提升性能”等目标。 |
| 理由 | 为什么选择这个方案？ | 将理由与背景中的需求和约束对应起来。 |
| 代价 | 这个选择带来哪些不足或限制？ | 说明接受的成本和约束，不只列优点。 |

推荐结构如下：

```markdown
# 决策：<名称>

## 背景

## 决策

## 理由

## 代价
```

### 参考示例：笔记采用软删除

以下示例展示各部分的写法。恢复期限和删除策略仅用于示例，不构成其他项目的需求。

```markdown
# 决策：笔记采用软删除

## 背景

产品要求用户能够恢复最近 30 天内误删的笔记。
如果删除时立即清除正文，恢复就需要依赖备份或其他副本。
需要确定删除后的数据保留方式。

## 决策

笔记采用软删除：记录删除时间，并在普通笔记列表和搜索中排除该笔记。
正文在恢复期限内保留，用户可以从回收站恢复。
恢复期限结束后，笔记进入永久清理范围。

## 理由

保留原笔记能够满足用户自行恢复的要求，无需为每次误删恢复备份。
记录删除时间能够确定恢复期限，也为后续清理提供依据。

## 代价

- 已删除笔记在清理前继续占用存储空间。
- 普通查询需要排除已删除笔记，遗漏过滤会导致展示错误。
- 系统需要提供恢复和永久清理能力。
- 软删除不代表数据已立即从存储中清除。
```

## Decision 不应写什么

- 完整的功能流程、边界情况和验收标准，应由 Spec 维护。
- 完整的系统结构和模块依赖，应由 Architecture 维护。
- 文件修改、任务顺序和验证命令，应由 Plan 维护。
- 执行进度和实际验证结果，应由 Status 维护。
- 与决策无关的讨论、重复争论和普通代码细节，不应为了保存聊天历史而全部写入。

Decision 可以简述方案以解释选择，但不应复制另一份完整设计。需要了解详细约定时，应引用对应文档。

## 与其他文档的分工

| 文档 | 负责的内容 | 软删除的示例 |
| --- | --- | --- |
| PRD | 产品目标与范围 | 用户可以恢复误删的笔记。 |
| Architecture | 系统结构和约束 | 笔记模块统一负责删除状态和存储访问。 |
| Spec | 功能行为与验收标准 | 明确恢复期限、恢复条件和清理后的结果。 |
| Decision | 选择及其理由和代价 | 说明为什么保留正文并采用软删除。 |
| Plan | 实施任务和验证安排 | 实现删除、回收站、恢复和清理。 |
| Status | 当前进展与验收结果 | 恢复功能完成，清理功能待实施。 |

当前有效的行为和结构约定以 PRD、Architecture 和 Spec 为依据，实际实现仍需通过代码和验证结果核实。Decision 保存理由，不应成为与 PRD、Architecture 或 Spec 竞争的另一份契约。

## 如何使用 Decision

需要理解已有选择时，读取对应 Decision，核对当时的问题、约束、理由和代价，再判断这些条件是否仍然成立。

引用历史决策时，应确认该选择是否仍然有效。过去采用某个方案，不代表它永远适合后续需求，也不代表实现已完成。

## 何时维护 Decision

形成需要长期保留的重要决策时，应及时记录，避免理由只留在聊天中。重要理由发生变化时，应更新或补充记录，不因普通代码修改反复重写。

| 变化 | 决策记录的维护方式 |
| --- | --- |
| 确认一项重要产品或技术选择 | 记录背景、决策、理由和代价。 |
| 补充原记录中遗漏的理由或限制 | 补充对应内容，不改变原决策含义。 |
| 新条件导致原选择被替代 | 记录新选择和变化原因，明确新旧记录的替代关系。 |
| 实现细节变化，但选择及理由不变 | 不需要因此更新。 |
| 决策对应的实现完成 | 结果记入 Status，不把执行日志追加到 Decision。 |

替代旧决策时，应保留理解历史所需的原有理由，不将旧记录改写成从未采用过旧方案。当前有效的产品、架构或功能文档应同步反映新的选择。
