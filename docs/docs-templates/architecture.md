# Architecture：架构文档的编写与维护

本文说明架构文档的用途、应包含的内容、与其他文档的分工，以及使用和维护规则。创建或更新架构文档时，可按本文确定系统结构、模块边界和约束的写法；开发过程中，可按本文判断变更是否需要同步架构文档。

## Architecture 是什么

Architecture（架构文档）是项目的权威系统级设计文档。它回答：系统如何组织，实现应遵守哪些结构规则。

架构文档描述系统的重要结构决策，包括系统边界、主要组成、模块职责、依赖关系、主要数据流和系统约束。这些决策通常影响多个功能；只服务一个功能但决定重要结构边界的设计，也属于架构。

架构文档维护已确认的设计约定。未确认的方案不作为有效架构约束，设计已确认也不代表实现已完成。实现进度和验收结果由 Status 维护，当前实现仍需通过代码和实际行为核实。

## 文件与权威入口

默认将主架构文档保存在 `docs/ARCHITECTURE.md`。一个系统通常只维护一份主架构文档，不应在没有实际需要时创建多个相互竞争的架构入口。

架构文档应在开头明确自身职责。例如：

> 本文是系统结构、模块边界、依赖关系和架构约束的权威依据。

不要过早拆分文档。只有当内容难以导航时，才将前端、数据、AI 或安全等专题拆入 `docs/architecture/`。主架构文档仍负责总体结构和导航，并链接详细文档。多个文件共同维护一份逻辑上的架构约定。

## Architecture 应写什么

以下是推荐内容。根据系统实际需要选用，不必为套用模板填充无关章节。

| 内容 | 应回答的问题 | 填写边界 |
| --- | --- | --- |
| 系统概览 | 系统由哪些重要部分组成，如何连接外部环境？ | 说明系统边界和主要组成，不罗列全部目录和文件。 |
| 技术栈 | 项目采用怎样的整体技术方案？各主要部分选用什么技术？这些技术如何配合运行？ | 说明整体技术路线、主要部分的具体选型、用途及关键兼容约束。按项目实际需要展开，与系统结构和部署方式保持一致，不复制依赖清单。 |
| 模块 | 每个主要模块负责什么？ | 说明职责、数据或状态的归属，以及模块之间的关系。 |
| 依赖规则 | 哪些模块可以依赖哪些模块？ | 说明方向和限制，避免只写“分层”“解耦”等无法判断实现是否合规的词。 |
| 数据流 | 主要请求和数据如何经过系统？ | 说明经过的模块、调用顺序和数据读写责任，不展开单项功能的全部分支。 |
| 外部服务 | 系统依赖哪些第三方服务？ | 说明服务用途、接入模块和访问边界，不复制第三方 API 文档。 |
| 架构约束 | 后续实现应遵守什么结构规则？ | 写重要结构边界和跨功能约束，不写单项功能的交互细节。 |

判断一条规则是否属于架构时，可以问：这条规则是否应适用于多个当前和未来的功能？如果是，它通常属于架构。

跨功能不是唯一条件。如果一项设计决定系统边界、重要模块的职责与依赖，或重要数据的归属，即使只服务一个功能，也应在架构中说明。例如，只有文件导入功能使用独立进程，进程隔离边界和通信关系仍属于架构。

例如，“所有外部 AI 调用都通过 `AIService`”属于架构规则。“删除笔记后跳转到笔记列表”属于功能行为，应由 Spec 说明。

推荐结构如下：

```markdown
# <系统名称>架构

本文是系统结构、模块边界、依赖关系和架构约束的权威依据。

本文描述 <系统或子系统范围> 内已确认的设计约定，不表示全部设计已经实现。

## 系统概览

## 技术栈

## 模块

## 依赖规则

## 数据流

## 外部服务

## 架构约束
```

### 技术栈的内容与边界

技术栈说明项目采用的整体技术实现方案。它应使读者能够判断系统用什么技术构建，各项技术承担什么工作，以及这些技术怎样组成可运行的系统。

技术栈应包含：

- **整体技术路线**：说明项目整体采用的技术体系和运行形态。语言、运行环境、核心框架及部署方式等内容，按项目实际需要展开。
- **主要部分的选型**：明确各主要部分采用的具体技术及用途。模块选型应符合整体技术路线。
- **组合关系与约束**：说明影响系统设计的技术连接方式和兼容限制，例如数据格式、调用方式、执行环境或资源共享条件。
- **选择状态**：区分已确认选择与待验证候选。候选应说明待验证的问题，不作为已生效的架构约束。

本节可简述选型的直接理由。需要长期保留的详细比较和取舍由 Decision 维护。本节不展开安装命令、实施步骤或普通局部实现细节。

### 参考示例：个人笔记产品

以下示例展示一个 Web 笔记产品的架构写法。技术栈、模块划分和约束仅用于示例，不构成其他项目的技术选型要求。

```markdown
# 个人笔记系统架构

本文是系统结构、模块边界、依赖关系和架构约束的权威依据。
本文描述已确认的目标架构，不表示全部能力已经实现。

## 系统概览

系统由浏览器前端和服务端组成。
前端提供笔记编辑、搜索和摘要界面，通过 HTTP 接口访问服务端。
服务端负责用户身份验证、笔记访问控制、数据保存和 AI 调用。

PostgreSQL 保存用户归属关系和笔记数据。
外部模型服务生成摘要，不负责保存笔记。

## 技术栈

| 部分 | 技术与用途 |
| --- | --- |
| 前端 | React、TypeScript，构建浏览器界面。 |
| 后端 | Node.js、TypeScript，提供 HTTP 接口并执行业务流程。 |
| 数据库与存储 | PostgreSQL，保存笔记正文及其归属关系。 |
| 认证 | 外部身份服务签发访问凭据，服务端验证凭据。 |
| AI | 外部模型服务，通过服务端 AI 模块接入。 |
| 部署 | 前端作为静态资源部署；服务端独立运行并连接数据库。 |

## 模块

| 模块 | 职责 |
| --- | --- |
| web | 展示笔记、接收用户输入、调用服务端接口和展示结果。 |
| api | 接收 HTTP 请求、验证输入、调用业务模块并返回响应。 |
| identity | 验证访问凭据，向业务模块提供已验证的用户身份。 |
| notes | 负责笔记创建、读取、修改、搜索、归属校验和保存。 |
| ai | 通过 AIService 接入模型服务，统一模型调用和重试。 |

notes 通过 NoteRepository 访问笔记存储。
生成摘要时，notes 负责读取用户有权访问的笔记，再调用 AIService。
ai 只接收本次生成所需的内容，不负责判断笔记归属或保存笔记。

## 依赖规则

- web 只能通过 HTTP 接口访问服务端，不直接访问数据库或模型服务。
- api 调用 identity 验证身份，再将用户身份和请求参数传给 notes。
- notes 可以调用 AIService；ai 不依赖 notes。
- notes 通过 NoteRepository 读写笔记，其他模块不绕过 notes 访问笔记存储。

## 数据流

### 保存笔记

1. web 将笔记内容和访问凭据提交给 api。
2. api 调用 identity 验证访问凭据。
3. api 将已验证的用户身份和笔记内容传给 notes。
4. notes 校验笔记归属，通过 NoteRepository 保存内容。
5. api 将保存结果返回 web。

### 生成摘要

1. web 将目标笔记标识和访问凭据提交给 api。
2. api 调用 identity 验证访问凭据。
3. notes 校验笔记归属，通过 NoteRepository 读取正文。
4. notes 将正文传给 AIService，由 ai 调用外部模型服务。
5. ai 将生成结果返回 notes，再由 api 返回 web。

摘要流程不写入笔记正文，失败也不触发正文修改。

## 外部服务

| 服务 | 用途与接入边界 |
| --- | --- |
| 身份服务 | 向用户签发访问凭据；服务端通过 identity 验证身份。 |
| 模型服务 | 根据输入生成内容；服务端统一通过 ai 接入。 |

模型服务密钥只在服务端使用，不发送到浏览器。

## 架构约束

- 笔记访问必须经过 notes 的归属校验。
- 所有笔记持久化都通过 NoteRepository，保持存储访问责任集中。
- 所有外部模型调用都通过 AIService，统一维护模型接入和重试规则。
- HTTP 入口负责协议转换，业务规则保留在业务模块中。
- AI 调用失败不能破坏已保存的笔记数据。
```

## Architecture 不应写什么

架构文档不应重复代码已表达的普通实现细节，也不应承担其他文档的职责。

- 单项功能的完整行为、页面状态和验收标准，应由 Spec 维护。
- 本次修改的文件清单、执行步骤和验证命令，应由 Plan 维护。
- 当前开发进度和验收结果，应由 Status 维护。
- 需要长期保留的选型背景、详细比较和取舍，应由 Decision 维护。
- 普通函数、类成员和局部算法，不应仅因它们存在于代码中就写入架构文档。

例如，“NoteRepository 包含 create、update 和 delete 方法”只是在复述代码。“所有笔记持久化通过 NoteRepository，保持存储访问责任集中”则说明了后续实现需要遵守的边界。

## 与其他文档的分工

| 文档 | 负责的内容 | AI 摘要的示例 |
| --- | --- | --- |
| PRD | 产品目标与范围 | 用户可以通过摘要回顾长笔记。 |
| Architecture | 系统结构和跨功能约束 | 外部模型调用统一经过 AIService，前端不直接调用模型服务。 |
| Spec | 具体功能行为 | 用户主动生成摘要，失败后可以重试，摘要不替换正文。 |
| Decision | 重要决策的理由 | 记录为什么集中模型接入，以及这种选择的取舍。 |
| Plan | 实施范围和任务安排 | 接通摘要接口、模型调用和结果展示。 |
| Status | 当前进展和验收情况 | 接口已完成，界面接入进行中。 |

产品要求可以形成架构约束，但架构文档不应重复整套功能行为。需要使用详细约定时，应引用对应文档，避免在多处维护同一规则。

## 如何使用 Architecture

理解产品目标后，读取架构文档，确认本次工作涉及的模块、职责、依赖和约束。随后读取已有且适用于本次工作的 Spec 和 Plan，并检查已有代码。

实现新功能时，应先确认已有模块和公共能力是否能够承担需求，避免重复建立职责相同的系统。不应为了简化局部功能而绕过系统级约束。

例如，架构要求外部模型调用统一经过 AIService，而 Plan 要求从 UI 直接调用模型服务，这属于架构冲突。应先解决冲突，再实施。

架构文档说明设计约定，代码说明当前实现。两者不一致时，应核实代码有误、文档过时，还是迁移尚未完成，不应默默选择其中一方。

## 何时维护 Architecture

当系统结构或跨功能约束变化时，更新受影响的架构内容。局部实现变化不应自动触发架构重写。

| 变化 | 架构文档的维护方式 |
| --- | --- |
| 修改按钮文字或删除后的跳转位置 | 不需要更新。 |
| 在既有模块中增加遵守当前约定的功能 | 通常不需要更新。 |
| 改变模块职责、依赖方向或数据归属 | 更新模块、依赖规则和受影响的数据流。 |
| 增加或替换外部服务 | 更新技术栈、外部服务及受影响的接入边界。 |
| 改变系统部署方式或持久化边界 | 更新系统概览和受影响的架构约束。 |
| 调整模块内部算法，结构规则不变 | 不需要因此更新架构文档。 |

更新时应检查总体入口与详细文档是否一致。重要决策的历史理由保留在 Decision，执行进度保留在 Status，不在架构文档中持续追加实施日志。

新设计替代旧设计时，应同步更新主入口和受影响的详细文档。仍需保留的旧文档应标记为“已被替代”，注明替代文档的位置，并移出当前有效架构的导航。历史文档可归档保存，不再作为后续实现的依据。
