# Spec：功能规格文档的编写与维护

本文说明功能规格文档（Spec）的用途、创建条件、应包含的内容，以及使用和维护规则。需要明确复杂功能的行为时，可按本文确定内容范围，并参考模板和示例组织文档。

## Spec 是什么

Spec（Specification，功能规格文档）定义单项复杂功能的具体行为。它回答：在什么条件下，用户或调用方可以做什么，系统应产生什么结果，以及怎样判断功能完成。

PRD 描述产品整体，Architecture 规定系统结构，Spec 则作为具体功能的行为契约。Spec 中的验收标准说明功能应达到的结果，不表示实现已经完成或验收已经通过。

## 什么时候需要 Spec

不是每个功能都需要 Spec。当功能存在较多歧义、风险或复杂性，仅凭简短任务容易产生错误假设时，应先明确 Spec。

可以问：执行者是否可能根据当前说明作出多种不同的实现决定？如果是，应通过 Spec 明确功能要求，减少实施中的猜测。

这里主要关注会改变功能行为、数据结果、权限或验收标准的不同理解。仅存在不影响行为契约的内部实现选择，不必因此创建 Spec。

| 通常需要 Spec | 通常不需要新建 Spec |
| --- | --- |
| 身份认证、授权、分享与权限系统 | 文案修改、简单样式修改 |
| 支付、文件上传、破坏性操作、数据迁移 | 行为明确的简单缺陷修复 |
| AI 处理流程、后台任务 | 小范围且不改变行为的重构 |
| 多步骤流程、复杂状态机、跨模块功能 | 已有模式下的简单增删改查功能 |

文档投入应与歧义和风险相称。不要仅因一项修改被称为“功能”，就要求创建 Spec。已有 Spec 能覆盖的行为变化，应更新对应文档，不必每次重新创建。

## 文件与职责范围

默认将 Spec 保存在 `docs/specs/<feature>.md`。通常一项复杂功能对应一份 Spec，由该文档维护功能行为和验收标准。

Spec 应明确功能名称、目标和范围。需要引用产品目标或架构约束时，链接对应文档，不在 Spec 中重新定义产品范围或系统结构。

## Spec 应写什么

以下是推荐内容。API 和 UI 状态等内容按功能实际情况说明，不应为了填满模板而新增接口或界面。

| 内容 | 应回答的问题 | 填写边界 |
| --- | --- | --- |
| 目标 | 功能让用户或调用方完成什么？ | 说明功能结果，不写编码任务。 |
| 前置条件 | 使用功能前应满足什么条件？ | 说明身份、权限、已有数据或外部条件，不把运行中可能发生的失败全部排除在外。 |
| 用户流程 | 用户如何发起并完成操作？ | 描述用户活动；后台功能可描述调用方或事件的触发流程。 |
| 行为 | 系统具体应做什么？ | 说明正常结果、限制和失败结果，不用“正常处理”代替规则。 |
| 数据 | 读取、创建、修改或删除什么数据？ | 说明数据含义和变化，不列出实现文件清单。 |
| API | 通过什么接口交互？ | 说明接口、输入、输出和失败；按实际情况描述 HTTP、IPC 或其他调用契约。 |
| UI 状态 | 不同阶段向用户展示什么？ | 覆盖适用的默认、加载、成功、空、禁用和错误状态；无界面时说明不涉及。 |
| 边界情况 | 非常规条件下应发生什么？ | 说明权限变化、重复操作、中断或部分完成等实际涉及的情况。 |
| 验收标准 | 什么结果证明功能符合约定？ | 给出可观察、可判断的结果。Plan 安排测试编写与执行，测试代码保存在项目测试文件中。 |
| 非目标 | 本功能明确不包含什么？ | 说明容易被误加的相邻能力，不重复整个产品的非目标。 |

推荐结构如下：

```markdown
# 功能：<名称>

## 目标

## 前置条件

## 用户流程

## 行为

## 数据

## API

## UI 状态

## 边界情况

## 验收标准

## 非目标
```

### 参考示例：单篇笔记摘要

以下示例展示各部分的写法。行为、接口和数据约定仅用于示例，不构成其他项目的需求。

```markdown
# 功能：单篇笔记摘要

## 目标

用户可以为已保存的笔记生成摘要，回顾主要内容并对照原文阅读。
生成摘要不修改笔记正文。

## 前置条件

- 用户已登录，并拥有目标笔记。
- 目标笔记已经保存。
- 目标笔记正文包含非空白内容。

## 用户流程

1. 用户打开一篇笔记。
2. 用户点击“生成摘要”。
3. 界面展示生成状态。
4. 生成成功后，用户在正文旁阅读摘要。
5. 生成失败时，用户查看错误提示，可以再次发起请求。

## 行为

- 系统在接纳请求时检查身份、笔记归属和正文内容。
- 每次生成使用请求接纳时读取的已保存正文。
- 未保存的编辑不参与生成，界面应说明摘要基于已保存内容。
- 同一页面正在生成时，生成按钮禁用，不能从该页面重复提交。
- 重新生成时，已有摘要保留到新摘要成功返回。
- 生成失败或返回空白内容时，展示错误，不替换已有摘要。
- 摘要只在当前笔记页面展示，不持久化，也不写入正文。

## 数据

读取：当前用户身份、笔记标识、笔记归属和已保存正文。

生成输入：本次请求读取的正文副本，后续编辑不改变该输入。

生成输出：非空白摘要文本。

本功能不新增、修改或删除持久化数据。
离开当前笔记页面后，界面清除摘要展示状态。

## API

操作：POST /notes/{noteId}/summary

输入：访问凭据和路径中的 noteId，不接收客户端提交的正文。

成功：返回 200，响应包含 summary 字符串。

失败：

- 401：用户未登录或访问凭据无效。
- 404：笔记不存在，或不属于当前用户。
- 422：已保存正文为空或仅包含空白字符。
- 502：模型生成失败或返回空白摘要。

## UI 状态

| 状态 | 展示与可用操作 |
| --- | --- |
| 默认 | 展示“生成摘要”按钮。 |
| 加载 | 展示生成提示，禁用生成按钮；已有摘要继续显示。 |
| 成功 | 展示摘要，允许重新生成。 |
| 空 | 已保存正文为空时，提示先保存正文，并禁用生成按钮。 |
| 禁用 | 正文为空或请求未结束时，不能点击生成按钮。 |
| 错误 | 展示失败原因；符合前置条件时允许重试，已有摘要保留。 |

## 边界情况

- 笔记在请求前已被删除：返回 404，不调用模型生成。
- 生成期间正文发生变化：本次摘要仍基于接纳请求时读取的内容。
- 用户离开页面后结果返回：不在其他笔记页面展示该结果。
- 网络请求失败：展示连接错误，保留已有摘要，允许用户重试。
- 摘要内容不符合用户需要：用户可以对照原文阅读或重新生成。

## 验收标准

- 有权访问的用户对非空笔记发起请求后，可以看到非空摘要。
- 用户可以在同一页面对照摘要和原文阅读。
- 无权访问目标笔记的用户收到 404，不能获得摘要。
- 正文为空时不发起模型调用，接口返回 422。
- 生成期间按钮禁用；正文变化不改变本次生成的输入。
- 生成失败时显示错误并保留已有摘要，笔记正文保持不变。
- 离开笔记页面后，旧请求结果不会显示在另一篇笔记中。

## 非目标

- 多篇笔记合并摘要。
- 自动生成或后台定时生成。
- 将摘要保存为笔记正文。
- 摘要历史和多版本比较。
```

## Spec 不应写什么

- 整个产品的目标与范围，由 PRD 维护。
- 系统级模块划分和依赖规则，由 Architecture 维护。
- 重要决策的历史背景与取舍，由 Decision 维护。
- 文件修改清单、编码步骤、测试命令和交付顺序，由 Plan 维护。
- 当前进度与实际验收结果，由 Status 维护。

Spec 可以定义功能所需的数据和接口契约，不应因此展开普通内部实现。文档应让实施者明确功能结果，同时保留不影响行为契约的实现选择空间。

## 与其他文档的分工

| 文档 | 负责的内容 | 笔记摘要的示例 |
| --- | --- | --- |
| PRD | 产品目标与范围 | 用户通过摘要回顾长笔记。 |
| Architecture | 系统结构和约束 | 模型调用经过统一接入模块，笔记存储由笔记模块负责。 |
| Spec | 功能行为与验收标准 | 摘要使用已保存正文，失败不覆盖已有摘要。 |
| Decision | 重要决策的理由 | 记录为什么摘要仅展示、不持久化。 |
| Plan | 实施任务与验证安排 | 实现摘要接口、界面状态和行为测试。 |
| Status | 执行进展与验证结果 | 接口完成，界面待验收。 |

Plan 应引用 Spec 的行为和验收标准，不维护另一套结果要求。验收标准变化时，应先同步 Spec，再调整实施和验证安排。

## 如何使用 Spec

理解产品目标和架构约束后，读取对应 Spec。明确前置条件、正常流程、失败行为、权限、边界情况和验收标准。若已有对应 Plan，同时读取其中的实施安排，再检查代码并实施。

实现应遵守 Spec 的行为契约，不应自行补充相邻功能。发现关键行为缺失或文档之间冲突时，应明确问题并确认约定，不把猜测直接写成需求或代码。

Spec 说明期望行为，代码和验证结果说明当前实现。两者不一致时，应核实是实现错误、文档过时，还是功能尚未完成，不应只为通过已有测试而改变需求。

## 何时维护 Spec

功能契约变化时，更新对应 Spec。实现方式变化但行为契约不变时，不必改写 Spec。

| 变化 | Spec 的维护方式 |
| --- | --- |
| 改变权限、输入、输出或失败结果 | 更新受影响的行为、接口和验收标准。 |
| 改变数据读写或状态变化 | 更新数据、行为、状态和受影响的边界情况。 |
| 修改内部算法，外部行为不变 | 不需要因此更新。 |
| 修复代码，使其符合现有契约 | 契约正确时不需要修改；遗漏的行为应确认后补充。 |
| 功能实现完成 | 验收结果记入 Status；仍有效的 Spec 继续作为行为依据。 |

后续修改同一功能时，应维护当前有效的 Spec，避免按开发批次积累多份相互竞争的契约。若新文档替代旧文档，应更新引用，并标明旧文档已被替代。历史资料不再作为当前功能行为的依据。
