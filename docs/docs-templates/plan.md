# Plan：实施计划的编写与维护

本文说明实施计划（Plan）的用途、应包含的内容，以及使用和维护方式。准备一次开发工作时，可按本文确定实施范围、任务安排和验证方式。

## Plan 是什么

Plan 定义当前要完成的实施工作。它回答：这次改什么、不改什么、依据什么要求、如何安排任务，以及怎样验证结果。

Plan 是阶段性的执行依据，不是长期的产品或功能契约。产品目标由 PRD 维护，系统结构由 Architecture 维护，功能行为由 Spec 维护。Plan 将这些约定转化为可执行的工作。

## 什么时候需要 Plan

当工作包含多个步骤、依赖或验证环节，需要明确执行范围和顺序时，可以建立 Plan。简单且边界明确的修改可以直接通过对话或任务系统执行，不必创建计划文件。

复杂功能应先明确需求和行为，再安排实施。不要用实施计划补齐未经确认的产品要求，也不要把大型功能压成一句模糊任务。

## 文件与职责范围

计划可保存在 `docs/plans/<work-item>.md`，也可在项目已有的任务系统中维护。选择一个执行入口，避免在文件和任务系统中重复维护同一份计划。

一份 Plan 对应一次边界明确的实施工作，可以包含多个任务。任务按工作依赖安排，不要求每个任务都单独建立文件。

## Plan 应写什么

| 内容 | 应回答的问题 | 填写边界 |
| --- | --- | --- |
| 目标 | 本次实施最终要交付什么？ | 写本次工作的结果，不复制整个产品目标。 |
| 依据 | 实施应遵守哪些约定？ | 引用适用的 PRD、Architecture、Spec 或已确认要求。 |
| 范围 | 本次具体改哪些内容？ | 列明实施内容；需要分步时说明任务和依赖。 |
| 约束 | 本次不改什么，哪些边界不能突破？ | 明确范围限制和已有约束，不自行新增需求。 |
| 验证 | 怎样证明本次工作完成？ | 引用验收要求，安排验证方式和完成条件。 |

推荐结构如下：

```markdown
# 计划：<工作名称>

## 目标

## 依据

## 范围

## 约束

## 验证
```

范围中的任务可以说明修改对象、任务结果和先后依赖。验证可以包含测试、类型检查、构建或人工操作，具体选择应与本次变化相称，不要求每次执行全部检查。

### 参考示例：实现公开分享笔记

以下示例假设分享行为已经由 Spec 确认。文档路径和任务仅用于展示写法。

```markdown
# 计划：实现公开分享笔记

## 目标

交付笔记只读公开链接的创建、访问和撤销能力。

## 依据

- docs/PRD.md：公开分享的产品范围。
- docs/ARCHITECTURE.md：公开访问与私有访问的结构边界。
- docs/specs/note-sharing.md：链接生成、权限、撤销和访问结果。

## 范围

| 任务 | 实施内容 | 依赖 |
| --- | --- | --- |
| P1 | 实现分享链接创建与撤销，补充对应行为测试。 | 已确认的分享 Spec。 |
| P2 | 实现公开只读访问入口，补充有效和已撤销链接的访问测试。 | P1 提供的分享状态。 |
| P3 | 接通创建、复制、撤销链接的界面操作和结果提示。 | P1 提供的接口。 |
| P4 | 验证完整分享流程，并检查私有访问行为。 | P1、P2、P3。 |

## 约束

- 不增加评论和协作编辑。
- 不重新设计身份认证。
- 不改变无关的笔记编辑行为。
- 不以公开分享入口替代已有的私有访问入口。

## 验证

依据分享 Spec 的验收标准安排以下验证，不重新定义预期行为：

- 运行创建、撤销和公开访问的行为测试。
- 检查无有效分享链接时，私有笔记不会通过公开入口泄露。
- 执行受影响代码的类型检查。
- 在两个浏览器会话中验证创建链接、只读访问、撤销和再次访问。

完成条件：本次范围已实现，适用的验收场景通过，实际验证范围已记录。
尚未执行的验证应标明，不能以代码提交代替验收结论。
```

## Plan 不应写什么

- 不重新定义 PRD 中的产品范围。
- 不为局部任务另立与 Architecture 冲突的结构。
- 不复制或改写 Spec 中的完整行为契约。
- 不把可能有用的相邻功能自动加入本次范围。
- 不将长期执行日志和阶段总结持续追加到计划中。

## 与其他文档的分工

| 文档 | 与 Plan 的关系 |
| --- | --- |
| PRD | 说明产品目标和边界，Plan 确定本次交付的部分。 |
| Architecture | 提供结构约束，Plan 安排符合约束的修改。 |
| Spec | 提供功能行为和验收标准，Plan 安排实现与验证。 |
| Decision | 保存重要选择的理由，Plan 安排落实选择的工作。 |
| Status | 记录项目进展、验收、阻塞和后续安排，并引用 Plan。 |

Plan 可维护任务勾选状态；Status 不复制整份任务清单，而是概述当前工作结果和后续安排。

## 如何使用 Plan

实施前，明确目标、范围、约束和验证要求，并读取计划引用的约定。检查已有代码后，再按任务依赖推进。

发现 Plan 与产品、架构或功能契约冲突时，应先解决冲突。执行过程中出现新的行为取舍，应确认并更新对应契约，不在计划里悄悄增加要求。

## 何时维护 Plan

| 变化 | 计划的维护方式 |
| --- | --- |
| 实施范围或任务依赖改变 | 更新目标、范围和受影响的任务。 |
| 功能契约改变 | 同步引用和实施安排，验证仍以有效契约为依据。 |
| 任务完成或被阻塞 | 更新任务状态，整体结果和阻塞说明写入 Status。 |
| 工作完成或取消 | 标明结果或终止情况，移出当前执行入口。 |

计划完成后，不再作为长期产品或功能依据。需要追溯时可归档保留；仍未完成且继续有效的工作应移交到后续计划或状态记录，避免随归档遗失。
