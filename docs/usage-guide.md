# 如何使用项目文档体系

本文介绍项目文档的职责分工、使用顺序和维护方式，并提供各类文档说明的入口。这套体系用于项目开始和持续开发，帮助维护明确、稳定的产品与系统约定，减少实施时的猜测。

`docs-templates/` 保存各类文档的说明与模板，`standards/writing-rules.md` 保存通用编写规则。项目实际的 PRD、Architecture、Spec、Decision、Plan 和 Status 按各自用途维护，不应将这里的参考示例当作项目已确认的需求。

## 文档分工

| 文档 | 回答的问题 | 说明入口 |
| --- | --- | --- |
| PRD | 构建什么产品，为谁构建，为什么构建？ | [产品需求文档](docs-templates/prd.md) |
| Architecture | 系统如何组织，实现应遵守哪些结构规则？ | [架构文档](docs-templates/architecture.md) |
| Spec | 具体功能在各种条件下应产生什么结果？ | [功能规格文档](docs-templates/spec.md) |
| Decision | 为什么作出某项重要选择，接受了哪些代价？ | [决策记录](docs-templates/decision.md) |
| Plan | 这次改什么、如何安排任务、怎样验证？ | [实施计划](docs-templates/plan.md) |
| Status | 当前在做什么，实际做到哪里，后续准备做什么？ | [开发状态](docs-templates/status.md) |

PRD 和 Architecture 分别是产品与系统架构的主入口。通常一个产品只有一份主 PRD，一个系统只有一份主架构文档。内容需要拆分时，主入口链接详细文档，避免多个文档竞争同一职责。

Spec 按复杂功能建立，Decision 按重要决策建立，Plan 按实施工作建立。Status 统一记录项目进展和后续安排，不另建一套重复的功能或架构约定。

## 开始项目时

先明确产品目标、用户、范围和非目标，再记录已确认的系统组织与约束。以 PRD 和 Architecture 为主要入口，不需要立即填满所有目录。

出现复杂或有歧义的功能时再创建 Spec；出现需要保留理由的重要选择时再创建 Decision。执行工作需要拆分时建立 Plan，进入持续推进时维护 Status。

项目的 `AGENTS.md` 可引用本文作为文档体系入口。通用编写要求见[文档编写规则](standards/writing-rules.md)，各类说明负责对应文档的用途、内容范围和维护方式。

## 开发时如何使用

本指南是文档体系的长期入口，首次进入项目或不确定文档分工时读取，不要求每次任务全文重读。

创建、修改或审查文档时，读取文档编写规则及对应类型的说明。普通代码开发不要求额外读取文档编写规则，也不必阅读全部类型说明。

以下流程中的 PRD、Architecture、Spec 和 Plan，均指项目实际文档，不是 `docs-templates/` 中的说明文档。

对于非简单工作，按以下顺序理解上下文：

1. 读取 PRD，确认产品目标和本次请求的范围。
2. 读取 Architecture，确认模块职责、依赖和系统约束。
3. 若已有适用于本次工作的 Spec，读取其中的行为、失败结果和验收标准。
4. 若已有当前工作的 Plan，读取其中的实施内容与验证安排。
5. 检查已有代码和测试，核实当前实现与可复用能力。
6. 完成本次范围内的修改，按契约和计划验证结果。

接续已有工作时，Status 提供当前状态、资料入口和后续安排。需要理解重要选择时，再查阅对应 Decision。

简单修改不要求创建或通读整套文档。阅读和维护范围应与任务的歧义、风险、影响范围、涉及模块数量、变更的不可逆性和长期影响相称。

## 收到新需求时

先判断变化影响哪类约定，再维护对应文档。

对于重要且难以撤销的选择，应判断是否需要 Decision 保存背景、理由和代价。

| 变化 | 主要涉及的文档 |
| --- | --- |
| 产品目标、范围或非目标变化 | PRD |
| 系统结构、职责或依赖变化 | Architecture |
| 具体功能行为或契约变化 | Spec |
| 形成需要长期保留的重要选择 | Decision |
| 实施任务、范围或验证安排变化 | Plan |
| 执行进展、阻塞、验收结果或后续安排变化 | Status |

不要为每次小改动创建全部文档。例如，修改按钮文字通常不需要更新 PRD 或架构；增加公开分享可能涉及产品范围、功能契约及实施计划；增加团队工作区则需要重新明确更广泛的产品和系统边界。

区分明确要求与可能扩展的能力。要求增加标签，不代表同时要求标签颜色、嵌套标签、AI 打标或权限体系。范围扩展应明确确认，不应在实施中自动生成。

## 信息归属与冲突

同一约定只在负责它的文档中维护完整定义，其他文档概述并引用。不同文档可以从各自角度提到同一功能，但不维护相互竞争的规则。

| 问题 | 判断依据 |
| --- | --- |
| 产品是否应包含某项能力 | PRD 中的已确认产品范围。 |
| 实现应遵守什么结构 | Architecture 中的有效约束。 |
| 功能应产生什么结果 | Spec 中的有效行为契约。 |
| 本次应完成哪些修改 | Plan 中的实施范围。 |
| 当前实际完成到哪里 | Status 中的记录，以及代码和验证证据。 |
| 为什么采用某项方案 | 对应 Decision 的背景、理由和代价。 |

文档说明设计意图，代码说明当前实现。两者不一致时，应核实是实现错误、文档过时，还是迁移尚未完成，不应默默选择一方。

Plan 不应悄悄改变产品或架构约定。历史决策和归档资料也不能覆盖当前有效的契约。当前明确提出的要求若改变已有约定，应指出变化并同步受影响的文档，不因旧文档存在就拒绝更新。

## 维护与收尾

产品、架构和功能契约变化时更新对应文档；内部实现变化但约定未变时，不必重写设计。已交付能力变化时同步 PRD 的能力概述，实际进展与验收边界记录在 Status。

STATUS 是了解和接续当前工作的统一入口。调研、规划、文档整理和开发都属于可记录的工作。记录应让读者了解当前工作、实际进度、尚未解决的问题和后续安排，并通过链接进入相关资料。

各小节按以下职责组织：

- **当前工作**：介绍正在做什么、目标和范围是什么、目前处于哪个阶段，并提供相关文档入口。这里概述整体状态，不展开逐项任务和验证细节。
- **进展与验收**：记录已完成的结果、实际验证范围和未验证部分。应区分实现完成、自动化验证通过和真实使用验收通过。保留判断进度所需的信息，详细证据通过链接引用。
- **待决策与阻塞**：说明需要决定的问题，以及实际阻止推进的条件和影响。不把普通待办或未经核实的疑点写成阻塞。
- **后续安排**：说明下一步工作及其启动条件，不复制 Plan 的完整任务清单，不把建议写成已确认的安排。

当前工作开始、取得实质进展、验收结论改变、阻塞出现或解除，以及后续安排或工作发生切换时，更新对应内容。当前工作以已明确的任务为依据，不因普通问答擅自切换。更新应反映当前状态，不按聊天、操作或日志顺序持续追加。

工作完成后，保留仍有效的产品、架构和功能约定。Plan 结束执行职责。

工作结束或切换时，概述结果，保留或移交仍有效的未完成事项，并更新当前工作和后续安排。需要追溯的详细历史可以归档，不在 STATUS 中持续堆积，不另建一份重复的进度记录。

文档被替代时，应更新入口和引用，并标明旧文档不再生效。Decision 保留历史理由及替代关系，避免丢失当时的选择依据。

实现完成、自动化验证通过和真实使用验收是不同结论。状态记录应说明已经验证的范围，不用一种结果代替另一种结果。

## 与其他资料的关系

编码、接口、测试等规范约束开发方式；操作指南说明具体工作如何执行；调研和讨论资料提供参考。这些资料不因存在于文档目录就自动成为产品或架构约定。

本体系不要求现有项目立即迁移文件或废止已有规范。采用新体系时，应明确替代范围并同步引用，避免新旧要求同时生效。文档类型说明和示例本身不代表已经完成项目规范切换。
