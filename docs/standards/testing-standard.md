# 测试规范

适用于测试方案设计、测试编写、修改和审查。日常执行 `AGENTS.md` 中的核心规则；需要判断具体场景时查阅本文对应小节进行明确判断。

## 一、测试目标与边界

- **必须验证用户或调用方关心的、已确认的行为，描述“能完成什么”，不得固定“内部怎么完成”。测试约束对外结果，不限制内部实现自由；行为不变的内部重构，测试仍应成立。**
- 行为依据必须来自用户已确认的需求、Spec 和设计决定。不得以现有代码或测试反向确定需求，不得为未确认的未来能力编写测试。
- 必须从能执行目标行为的最近现有公开接口进入，观察该接口或相关公开接口提供的结果；不要求所有测试都经过完整应用。
- 禁止直接测试私有方法、绕过接口检查内部状态，或用内部协作者的调用次数、调用顺序证明功能正确。
- 协议字段、外部请求次数、事件顺序等本身属于已确认契约时，必须按契约验证，不得将其误判为内部细节。
- 测试数据库迁移、外键、唯一约束等存储契约时，可以直接使用 SQL；普通业务行为仍通过公开接口验证结果。

## 二、真实执行与结果判断

- 被测行为必须由真实实现执行；禁止替换核心逻辑后，仅验证假对象按预设方式工作。
- 仅在外部服务、时间、随机数等系统边界按需使用替身；不得模拟内部协作者来固定实现过程。数据库优先使用隔离的真实测试数据库。
- 故障注入必须限制在目标故障处，保留其余真实流程；不得在测试中复制生产流程。
- 预期结果必须具有独立依据，如已确认的规则、已知正确样例或外部协议；禁止调用被测实现生成预期值，或照搬被测算法计算预期值。
- 一个测试必须围绕一个明确行为；允许多条断言共同证明该行为，禁止混入无关规则，不得为了减少断言数拆散完整行为。
- 不得固定未经对外承诺的错误全文、内部 ID 格式、辅助类结构或临时文件命名。

## 三、场景选择与测试维护

- 新增前必须检查已有覆盖，明确目标行为、缺失条件和可观察结果；优先复用或调整已有测试。
- 不得因新增文件、修改代码或修复缺陷机械增加测试。已有测试能准确暴露目标缺陷时，使用该测试验证修复即可。
- 补充场景必须对应有区别的行为条件、规则边界或失败结果；不得机械枚举全部参数组合，或仅替换等价数据增加用例。
- 同一规则应有主要验证位置；其他层保留接入及组合行为所需的验证，不重复完整规则矩阵。
- 已确认行为改变时，必须更新或删除失效预期；不得为了保住测试而保留错误实现。
- 合并或删除测试前，必须确认没有丢失独立行为、不同接入点或不同失败后果的覆盖；不得仅凭名称、行数或用例数量裁减测试。

## 四、TDD 执行

- 按已确认的测试方案逐项执行：选定一个行为 → 使用或补充测试并确认失败 → 实现使其通过 → 通过后按需重构 → 处理下一个行为。
- 失败证据必须对应目标行为；不得把无关的导入错误、配置错误或环境故障视为有效的失败验证。
- 禁止先批量编写全部测试再批量实现；禁止在测试通过后夹带未经确认的能力。
- 行为不变而测试因内部重构失败时，必须检查实现是否破坏行为、测试是否绑定内部细节，不得机械修改断言以求通过。

## 五、稳定性与验证

- 测试必须隔离数据、环境变量和资源，不得依赖执行顺序或使用业务数据库；临时资源必须清理，真实服务调用必须单独显式启用。
- 并发测试必须使用可控事件等方式建立所需时序，不得靠固定等待时间猜测任务完成；超时仅用于防止无限等待。
- 测试辅助代码必须保持简单，不得重新实现生产功能。
- 测试不稳定时必须查明原因，不得通过放宽正确性断言、反复重试直到通过或跳过测试掩盖问题。
- 必须运行与改动相称的测试和项目必要检查；通过后，仅在新改动、新失败或未解决疑点需要时扩大或重复验证。
- 必须如实记录实际执行范围、结果和未执行项；不得将测试收集成功或离线测试通过表述为真实服务联调通过。
