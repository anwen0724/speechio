# React + TypeScript 前端编码规范

更新日期：2026-09-12

本文适用于当前 React + TypeScript 前端的新增、修改和重构，包括组件、Hook、状态、数据访问、样式及测试。目标是结构清晰、类型安全、交互可靠、便于持续修改。具体产品行为和目录结构由对应 spec 维护。

“必须／禁止”表示要求；“应当／避免”表示默认做法，例外应有具体理由；“优先／考虑”表示设计倾向。按实际职责判断，不机械套用文件数量、代码行数或分层模板。

## 首要规则：先建立页面布局骨架，再填充功能组件

新增或调整页面时，必须先确定整体分区及布局骨架，再在各区域中实现具体组件，最后完善视觉样式。修改已有页面前，必须先检查并沿用其布局骨架；骨架不足以承载需求时，先调整骨架，不能先拼组件再靠样式补丁修补布局。

- 页面布局层统一负责区域划分、尺寸分配、定位、响应式及滚动归属，明确哪些区域固定、哪些伸缩，以及侧栏是占用空间还是覆盖显示。
- 功能组件负责所在区域内部的内容、交互和局部布局，不自行改变整页宽度、定位其他区域，或通过修改 `html`、`body` 的样式修补局部布局。
- 加载、空内容、长内容及面板开关必须遵循同一套布局约束；除非产品明确要求，不得推动无关区域或改变整页滚动方式。局部侧栏与全局模态弹窗必须按各自职责处理。

开发与提交前必须首先检查上述要求，不能以组件拆分完成或编译通过代替布局职责检查。

## 1. 先把组件写清楚，再决定是否复用

使用 React 函数组件组织界面。组件应当能用明确的名称说明它展示或处理什么，例如消息输入框、笔记编辑器、资料预览。

先围绕当前页面实现清晰的结构和行为。多个地方确实需要相同的界面或交互时，再考虑提取公共组件或 Hook；不要只因为两段 JSX 看起来相似，就做成包含大量配置和条件分支的通用组件。

按钮、输入框、弹窗等优先使用项目已有的通用组件。只在一个功能使用的组件留在该功能附近，不提前搬入公共目录。

提取后的组件应当让使用处更容易理解和修改。如果调用者仍需传入大量内部状态、控制每个细节，应重新检查组件的划分。

## 2. 按前端职责组织文件，不机械分离视图与逻辑

组件的 JSX、Props、局部状态、事件处理、简单校验和专用辅助函数可以放在同一文件。这些代码共同完成一项界面职责，不因为出现多种语法就必须拆分。

例如消息输入组件可以同时处理文字、附件展示、输入法、发送快捷键及提交前校验；不要求拆成组件、Hook、校验器、事件处理器四个文件。

页面可以组合多个功能区域、读取路由参数并协调导航。页面不承担各区域的全部实现；请求、浏览器存储和多个视图共用的保存规则，放到对应功能的代码中。

出现以下情况时再考虑拆分：

- 一部分有独立的界面或交互职责，会因不同需求而变化。
- 多处确实需要复用相同的状态行为或界面。
- 数据读取、保存或流式回复等逻辑已经复杂，单独组织更容易理解和验证。
- 嵌套、分支或副作用妨碍阅读，拆分能够减少理解成本。

没有统一的文件或函数行数上限。紧密相关且通常一起修改的代码可以保留在一起。自定义 Hook 可以复用状态行为，也可以整理复杂逻辑，但不为每个组件机械配一个 Hook。

## 3. 按功能聚合，保持依赖方向清楚

遵循项目 spec 中的目录结构：

- app：应用入口、路由、布局及必要的全局协调。
- pages：页面组合与路由相关的交互。
- features：按功能聚合组件、操作函数、共享状态和类型。
- shared：真正通用的 UI 与基础能力，不放无关功能的集合。
- tests/fixtures：仅供测试使用的样例与 HTTP 响应，生产代码不导入测试数据。
- styles：全局设计变量和基础样式；具体功能样式按职责组织。

局部使用的组件、Hook 和类型留在功能附近。只有存在明确复用或独立职责时才拆文件，不预建空目录。

共享数据的类型由对应功能维护。整份浏览器保存数据的校验等跨功能代码可以放在应用入口附近，但不能因此建立收集全部功能类型的全局 types.ts，也不重复定义同一类型。

不要经由另一个功能的页面组件读取数据，避免循环依赖。不要求为每个目录建立仅转发导出的 index.ts。避免把不相关的函数堆进 utils.ts、helpers.ts 等模糊命名的文件。

## 4. 组件接口与文件内容保持直接

Props 表达组件真正需要的数据和动作。简单展示组件接收内容和回调，不为获取一个字段而依赖整份应用状态。

使用 children 等方式组合界面；不要把布局、数据获取和多个互不相关的用途全部塞入一个复杂配置对象。组件不能直接修改传入的 Props。

优先 named export，只导出实际被其他文件使用的能力。框架约定需要 default export 时可以使用。组件与 Hook 遵守 React 调用规则，不在条件、循环或普通事件回调中调用 Hook。

文件优先按 imports、必要的常量与类型、主要组件或导出函数、辅助实现组织。Schema 推导类型、框架入口等可以采用更自然的顺序。复杂渲染分支可以拆成职责明确的区域或子组件，避免堆叠难以阅读的三元表达式。

## 5. 命名表达界面或操作的含义

组件名使用 PascalCase，Hook 使用 use 前缀，其他函数和变量使用清晰的动作或对象名称。文件名沿用项目约定并表达主要职责。

使用 conversationId、selectedNote、saveDraft、cancelGeneration 等名称。避免缺少上下文的 data、info、handleData，或用 result2 等临时名字长期承载明确含义。

事件处理可以使用 handleSubmit、onSelect 等上下文清楚的名称，无需制造冗长表达。布尔值应能读出含义，例如 canSubmit、isArchived。

## 6. 状态放在合适的位置

输入、焦点、展开状态等优先放在组件或局部 Hook。确实需要跨区域共享的数据才进入共享状态。

筛选条件、选中的资源等需要支持链接、刷新和前进后退时，可以由路由表达。避免 URL、局部状态和共享 store 各保存一份相同值而缺少明确来源。

可以从现有数据计算出的值，优先直接计算，不通过 Effect 再维护副本。例如剩余题数从题目与作答记录得出。

编辑草稿与已保存内容是两种有意义的状态，可以分别保存；要明确保存、恢复、放弃和外部更新时的行为。

同一篇笔记、同一个计划在不同视图使用同一数据来源。跨区域更新通过稳定标识和明确操作完成，不能直接修改 React state 或外部 store 提供的对象。

共享 store 的订阅尽量选择当前组件需要的部分。不要让每次按键都触发整个工作台无关区域的更新。

## 7. 用类型表达互斥状态

对于互斥且带有不同附加数据的流程，优先使用可辨识联合：

```ts
type SaveState =
  | { status: 'idle' }
  | { status: 'saving' }
  | { status: 'failed'; message: string };
```

避免用可能互相矛盾的多个布尔值表示同一流程。彼此独立的状态可以分别维护，例如导航展开与笔记编辑；不必强行合并为一个巨大的状态机。

状态分支应处理完整。数据刷新时保留旧结果、同时展示刷新状态等组合，应根据真实需求表达，不机械要求所有状态只剩一个字段。

## 8. TypeScript 类型安全与数据校验

启用严格类型检查，不通过 any、非空断言或双重断言绕过错误。未知输入使用 unknown，再通过类型守卫、Schema 或其他运行时验证获得可信类型。

API 响应、浏览器持久化内容、导入文件、URL 参数及跨窗口消息等外部输入，要在读取和使用之前验证。JSON.parse、response.json 和类型断言都不等于完成校验。

校验强度与用途相符：简单标识可以检查格式及对象是否存在，不要求一律引入 Schema。校验后内部使用可信类型，不在每个组件或函数中重复解析。

Props、事件和回调优先利用类型推导。只在局部使用的类型靠近使用位置；共享类型随所属功能维护。已有 Schema 时可以推导类型，避免两份结构不一致。

catch 的值按 unknown 处理。类型断言只用于表达已经验证而 TypeScript 无法推导的事实；必要的第三方兼容例外限制在相关代码附近并说明原因。

## 9. 渲染保持纯粹，Effect 用于外部同步

渲染过程不启动请求、不写存储、不修改外部状态，也不临时生成列表记录的身份。记录 ID 在创建操作时生成，列表使用稳定 ID 作为 key；可增删或重排的列表不使用数组下标代表身份。

用户点击触发的保存、提交、开始学习等操作，由事件处理流程明确发起，避免因刷新或重新挂载造成重复执行。

Effect 用于与外部系统同步，例如订阅、浏览器监听或读取与当前视图有关的数据；依赖必须完整。不要压制依赖检查来规避设计问题，也不使用 Effect 保存本可直接计算的值。

Effect 返回相应清理逻辑。初始化、订阅及清理应能承受 StrictMode 下的额外检查，不通过移除 StrictMode 掩盖重复执行问题。

## 10. 请求与流式回复明确归属、取消与过期处理

Promise 必须被等待、返回，或具有完整的错误处理。单独使用 void 不会处理 Promise 的拒绝。

页面不再需要的临时读取可以取消。需要继续接收的会话回复则应写回原会话，不能写入当前恰好打开的页面。

取消请求与忽略过期结果是不同问题。通过请求标识、目标记录标识或版本检查，防止迟到响应覆盖新的状态。停止后的旧片段不能重新把回复变成生成中。

独立读取可以并发；涉及同一份保存数据或文件与元数据先后关系的更新，采用串行或受控并发。大量文件处理不能无上限并发。允许部分成功的读取应分别呈现结果，不让一个失败掩盖其他成功结果。

清理监听、定时器和临时 Object URL；资源需要保持到用户不再使用时，不能因无关渲染提前释放。

## 11. 数据访问与界面分离

页面和展示组件不直接访问 localStorage、IndexedDB，也不直接导入模拟数据。通过所属功能提供的读取、保存等函数完成操作。

这些函数负责集中处理接口或浏览器存储的差异、校验和错误。不要在它们外面增加多层只转发参数的包装。模拟与真实实现提供界面需要的相同操作，组件不承担大量环境分支。

明确“保存成功”的含义。持久化未成功时不能仅凭内存更新就宣称成功。采用乐观更新时，应明确失败后的回滚或待重试状态，并保留用户输入。

请求或存储失败不得静默清空用户数据。数据格式变化需要明确版本与兼容处理；无法恢复时呈现问题并保留可恢复的原始内容。

## 12. 表单与事件构成完整的用户操作

根据实际需要使用受控或非受控表单，不要求所有输入进入全局 store。可提交的表单应处理提交事件，字段有明确标签与错误关联。

校验失败保留输入并说明可修正的问题。防重复提交的范围与具体操作一致，不因一个请求锁住整个应用。

发送快捷键兼容中文输入法，选词回车不能触发提交。多行输入、Enter 与组合键行为符合已确认产品约定。

事件处理可以顺序完成校验、调用和反馈；只有复杂度或职责独立时才拆分，不按语法步骤拆成多个文件。

组件需要通知上层时，使用含义明确的回调或对应功能操作，不直接修改传入的数据。

## 13. 错误必须可观察、可恢复

能恢复、补充必要说明或向用户呈现时才捕获异常，不在每层重复 try/catch。

事件回调、流式回调和请求入口必须保证失败最终得到处理。区分主动取消、校验失败、网络错误和程序异常，给出相应反馈，不把取消误报为故障。

失败不清空未保存输入；重试不能无意重复创建记录。已经成功的保存与随后失败的列表刷新应分别呈现。

React 错误边界用于兜住渲染故障，不能替代事件处理和异步错误处理。应用级错误可以提供重试或返回入口，不以无限刷新掩盖问题。

日志不包含密钥或完整敏感输入。错误信息通过安全的文本方式展示；不能把未知异常直接断言为 Error 后读取属性。

## 14. 注释说明必要的职责、边界和原因

注释默认使用简短英文。负责复杂数据读写、共享状态或流式处理的文件，应有简短文件头说明职责及主要协作对象。

简单展示组件、含义明确的类型文件、框架配置和自动生成文件不强制添加文件头。

具有非显然保存规则、错误行为或副作用的公开操作，以及有清理要求的 Hook，必须用 JSDoc 说明必要行为。输入、输出、顺序或资源释放要求不明显时一并说明。

简单组件、纯函数和 Props 不强制写重复注释。非平凡内部逻辑，特别是并发、取消和数据一致性处理，应说明关键原因。

不为每个匿名回调添加注释；复杂回调需要独立理解时再提取。注释不能代替清晰结构，代码变化时同步维护，不能保留过时描述。

## 15. 样式组织与响应式布局

先落实本文首要规则中的页面骨架与区域职责，再组织各区域及组件的样式。

使用项目确定的样式方案与设计变量，统一颜色、间距、字号、圆角和层级。通用组件维护通用外观，功能样式留在对应范围；不要为单个功能添加影响全站的宽泛选择器。

Tailwind 类、组件样式和必要的动态 style 可以按用途组合，不要求所有样式采用一种写法。动态值与样式变化放在最容易维护的位置，避免反复覆盖和大量 !important。

布局适应可用空间，不只针对一张桌面截图。长标题、代码、公式、表格和用户输入不能撑破页面；必要时让内容区域滚动，保持导航及主要操作可达。

明确层级与滚动归属，避免多个固定区域、弹窗和抽屉互相遮挡。移动端不能仅把桌面多个侧栏压窄，应按阅读和操作需要组织主内容与辅助区域。

## 16. 语义、键盘和动画属于实现要求

导航使用链接，动作使用按钮；非必要不以可点击 div 代替。图标按钮有可访问名称，表单有标签，错误和状态变化在合适区域可被辅助技术感知。

键盘可以到达主要操作，焦点清楚。弹窗和抽屉处理焦点进入、限制与返回，遵循组件库的交互约定，不重复实现容易冲突的焦点逻辑。

信息不只依靠颜色表达。选择、展开、禁用和生成状态应能辨认。用户内容按安全的 Markdown 或文本规则渲染；未经清理的 HTML 不能直接注入，外部链接限制不安全协议。

动画用于帮助理解状态变化，避免影响输入与阅读。尊重 prefers-reduced-motion，不依赖动画完成后才允许核心操作。

## 17. 按实际问题优化性能

不默认到处添加 memo、useMemo 和 useCallback。只有存在明显计算成本、渲染问题或引用稳定性要求时使用，并保持依赖正确。

优先避免重复状态、无关全局订阅、重复读取和不必要的网络请求。流式内容更新应限制到相关区域，不每个字符重建整个工作台。

列表虚拟化、延迟加载和资源拆分根据数据量与实际表现决定，不为尚不存在的规模引入复杂框架。优化不能改变保存、取消等用户操作的结果。

## 18. 测试实际行为，维护可重复的检查

测试重点放在可见行为、数据一致性和容易回归的边界：输入保留、取消与重试、跨页面关联、存储失败、刷新恢复、键盘与表单操作等。

不为简单可逆样式改动机械增加单元测试，不编写只复述实现的测试。保存规则和流式处理可用单元测试，集成流程用组件或浏览器测试；按范围选择，不要求每层重复覆盖同一断言。

浏览器检查包含必要的宽度、长内容和失败状态，不以构建通过代替交互或视觉验收。测试使用独立数据，避免污染用户日常记录；模拟结果不能证明真实后端和模型能力。

代码提交或交付前运行与改动相称的类型检查、代码检查、构建和测试。未执行或未通过的项目明确记录，不用一个局部通过结果宣称整个产品完成。

## 19. 修改现有代码时控制范围

先理解附近命名、组件组织、数据流和错误处理，优先保持局部一致性。已有代码违反正确性、类型安全或已确认行为时，不继续复制问题。

不要因小改动顺手重构无关功能。新依赖应解决明确问题；不为一个简单行为增加整套框架，也不重复实现项目中已经合适的通用组件。

格式遵循项目配置。文档、样例和测试与实际行为一起维护，避免规范与实现计划互相矛盾。

## 20. 完成前自检

- 首先检查：是否先建立页面分区骨架，区域尺寸、定位和滚动是否由布局层统一管理，功能组件是否越界影响整页或其他区域？
- 组件、页面和操作函数是否清楚，是否存在机械拆分或无意义包装？
- Props、Hook 和共享状态是否真的需要当前依赖范围？
- 是否存在重复状态、不必要的 Effect 或渲染副作用？
- 外部输入是否在读取时校验，是否用断言掩盖错误？
- 请求归属、取消和迟到结果是否明确，所有失败是否得到处理？
- 保存失败、重试、切换页面和刷新后是否保留正确内容？
- 代码、公式、长文及窄屏布局是否可用？
- 表单、焦点、快捷键和中文输入法是否正确？
- 注释是否补充必要信息，是否存在过时或重复说明？
- 验证是否覆盖实际改动，是否仍有未完成的要求？

优先保证正确与类型安全，再保持清楚、简单和易维护。不能为了抽象、文件数量或形式一致，牺牲实际开发与使用体验。
