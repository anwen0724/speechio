# 关系型数据库与库表设计规范

版本：1.0

更新日期：2026-09-13

适用范围：关系型数据库的新增设计、表结构变更与设计审查，以在线业务系统为主要应用场景。分析型数据库、时序系统和非关系型存储需要另行补充相应方法，不能直接套用全部实现选择。

本文将数据库理论、官方文档和工程实践整理为可执行的设计要求，不是一份数据库产品标准，也不以某个具体功能作为通用模型。文中“必须／禁止”是采用本规范后的项目要求；“应当／默认”允许在说明依据后调整；“可以”表示可选方案。

## 1. 首要原则：先说明数据与规则，再推导表结构

**设计必须展示需求、数据含义、关系、约束到表结构的推导过程。禁止先定表数、先列表名，再寻找理由；也禁止随质疑增减表数而不重新检查整体模型。**

- 表数、字段数、代码模块数都不是设计质量指标。新增一张表或合并两张表，都应说明解决了什么具体问题。
- 数据模型表达需要保存的信息及其约束，不直接照搬页面、接口 DTO、Service、流程步骤或对象类。
- 先检查既有概念、表和数据来源，明确复用、扩展与新增边界。局部设计不得造成全局同义异名、同名异义或多个互相矛盾的数据来源。
- 未确认需求、已确认规则和设计假设必须分开记录。不能把推测的未来需求作为当前必须建表的理由。
- 理论约束、业务约束、数据库产品行为和工程偏好必须分开说明，不以“规范如此”代替证据。

设计阶段的划分依据数据需求、概念模式、逻辑模式和物理实现之间的区别；它们是逐步细化的关系，也允许通过验证回到前面修订。[教材：E-R 设计](https://www.db-book.com/slides-dir/PDF-dir/ch6.pdf)

## 2. 设计流程与交付要求

| 阶段 | 核心工作 | 应有的可检查结果 |
| --- | --- | --- |
| 需求分析 | 明确用途、使用者、读写操作、数据范围、时效与不可违反的规则 | 数据需求、术语和业务规则清单；已知与未知边界 |
| 概念设计 | 识别对象、事实、属性及关系；说明数量、可选性和存在依赖 | 概念关系图与定义，不急于给字段类型或索引 |
| 逻辑设计 | 明确记录粒度、候选键、依赖、关系映射和完整性 | 逻辑表结构、键、约束及拆合依据 |
| 物理设计 | 结合目标 DBMS、容量和读写方式选择实现 | 字段字典、DDL、索引和必要的存储选择 |
| 行为验证 | 检查查询、增删改、并发、重试、故障与时间边界 | 样例、事务过程、验证结果及尚未覆盖项 |
| 演进维护 | 处理已有数据、旧版本程序和部署过程 | 迁移、兼容、回填、恢复与后续维护安排 |

这不是要求一次设计全部未来功能。小变更可以用一段说明和一张字段表完成相关检查；没有影响的部分注明“不涉及”，不能为形式复制整套文档。跨多个实体或改变已有数据含义时，必须回到整体关系与读写过程进行检查。

需求既包括输入，也包括需要回答的问题和需要执行的操作。仅列页面字段不能证明数据需求完整；范式检查同样不能发现所有遗漏需求。[Microsoft：数据库设计基础](https://support.microsoft.com/en-us/access/database-design-basics)

## 3. 决定保存什么：依据用途、来源和生命周期

每项拟持久化数据至少回答：谁产生和维护、谁使用、丢失有什么后果、需要保留多久、能否可靠重建、是否需要历史。

| 数据性质 | 判断要求 |
| --- | --- |
| 当前业务状态 | 明确覆盖更新是否符合含义，以及谁拥有修改权 |
| 已发生的业务事实 | 明确是否需要保持发生时的内容、身份和时间 |
| 系统配置 | 根据维护方式、共享范围、版本和查询需求选择配置文件、配置服务或数据库；不自动建配置表 |
| 技术日志和观测信息 | 根据诊断、保留与查询需要选择日志或观测存储；不将每个执行步骤变成业务表 |
| 临时状态 | 无恢复要求时可放内存；影响并发准入或故障恢复时可能需要可靠存储 |
| 派生值和汇总 | 默认从权威数据计算；确需保存时明确更新、校验与重建机制 |
| 缓存 | 明确权威来源、过期、失效和失败语义，不能不知不觉变成唯一事实来源 |

“需要持久化”不等于“必须进入业务关系数据库”；“是中间状态”也不等于“可以丢失”。以上是工程判断框架，不按数据名称机械分类。

当前值与历史快照必须区分。例如商品当前价格与订单成交单价表达不同时间的事实，不应因字段数值相同而被当作同一份冗余。单个 `updated_at` 不能恢复此前内容；需要时点查询时，必须设计版本或历史表达。系统版本时间与业务生效时间也不能未经说明混用。[Microsoft：时态数据](https://learn.microsoft.com/en-us/sql/relational-databases/tables/temporal-tables?view=sql-server-ver17)

## 4. 概念、记录粒度与关系

### 4.1 定义而不是猜测实体

- 先用业务语言定义概念，说明不同实例如何区分、何时产生、何时结束，以及与其他概念的联系。
- 实体可以表示对象、事件或概念，不限于现实中的物品。不能因它是一个名词就建表，也不能因它源于动作就一律否定建模。
- 数据库中的实体、面向对象程序中的类、DDD 中的实体与聚合不是可以直接互换的词。需要采用某种架构术语时，必须说明其定义和适用层次。
- 实体与表没有普遍的一一映射要求；关系和多值属性也可以映射为表，一个概念也可能因明确的实现原因映射为多个结构。

对象、事件、概念的识别需要结合信息需求；不同资料对“概念模型／逻辑模型”的命名也有差异，交付物应以实际包含内容为准。[IBM：数据建模](https://www.ibm.com/think/topics/data-modeling)

### 4.2 每张表先写一句记录定义

必须能回答：“一行表示什么？在哪个范围和时间语义下唯一？”

例如“一个学生”“一门课程的一次开课”“一个学生对一次开课的选课”是不同粒度。不能把不同粒度的数据混入同一行，然后依赖大量空字段猜测其含义。

字段必须能够说明描述的是这条记录、它关联的对象，还是某个时间点的快照。不能仅因多个字段都关联同一个用户，就认定它们属于同一张表。

### 4.3 显式表达关系

- 标明双方的一对一、一对多、多对多，以及 `0..1`、`1..1`、`0..N`、`1..N` 等参与约束。
- 标明关系本身的属性、能否重复发生及是否有独立有效期；不要只画一条无含义的连线。
- 一对多通常在多方表达引用，多对多通常通过关联表表达；具体映射必须保留原有数量和可选性约束。
- 一对一允许合表，也允许分表，应比较主题、可选性、生命周期、访问权限和实际读写需求。它只限定数量，不能单独决定拆合。
- 不建立已经能由现有键与关系完整表达的重复关联，除非有明确的历史或性能用途并维护一致性。

Oracle 的建模文档区分逻辑实体、关系模型和物理模型，并明确关系到表的映射；映射是一项设计工作，不是照抄类结构。[Oracle：模型与映射](https://docs.oracle.com/en/database/oracle/sql-developer-data-modeler/18.2/dmdug/data-modeler-concepts-usage.html)

## 5. 键、函数依赖与规范化

### 5.1 先确定业务唯一性

- 列出能唯一识别记录的候选键，再决定主键。候选键是最小超键，“最小”指不能删除其中任一属性后仍保持唯一，并非长度最短。
- 自增 ID、UUID、雪花 ID 等是标识实现选择，不替代业务唯一约束，也不能消除原有属性依赖。
- 自然键与代理键的选择应考虑稳定性、宽度、引用成本和业务变化；禁止规定所有场景必须使用同一种形式。
- 唯一性需要说明范围，例如全局、租户内、父对象内、某个业务周期内。样例当前不重复不是业务唯一性的证据。

### 5.2 用依赖检查属性归属

函数依赖 `X → Y` 表示在所有合法数据状态中，相同的 X 必须对应相同的 Y。它来自业务约束，不是从少量现有记录推断出来的偶然规律。

例如，在“每个员工当前属于一个部门”的规则下：

```text
员工编号 → 员工姓名、部门编号
部门编号 → 部门名称
```

将部门当前名称复制到每个员工行，会增加重复维护与不一致风险。应根据依赖分析是否分离；如果保存的是历史任职时的名称，则先区分时间含义，再分析依赖。[伯克利 CS186：函数依赖](https://cs186berkeley.net/notes/note13/)

### 5.3 规范化与分解检查

以下“主属性”指属于至少一个候选键的属性，“非主属性”指不属于任何候选键的属性。2NF 以满足 1NF 为前提；范式判断针对关系模式及其全部有效依赖。

- 1NF：按选定的数据模型和属性域表达单值，不使用逗号拼接等方式藏匿需要独立关联的数据集合。JSON 类型的使用需要单独说明查询与约束边界，不能仅凭用了 JSON 就判定合格或不合格。
- 2NF：非主属性不能只依赖某个候选键的一部分。检查所有候选键，而非只检查新增加的代理主键。
- 3NF：对每个非平凡函数依赖 `X → A`，X 为超键，或 A 属于某个候选键。以正式条件为准，不用口号替代复杂情况下的判断。
- BCNF：每个非平凡函数依赖的决定因素都必须是超键。更高范式仅在出现对应依赖问题时使用，不机械追求级别。
- 分解必须无损：关联后能恢复原来的信息，不丢失记录、不制造虚假的组合；尽量保持依赖，使原有约束仍能有效检查。
- 规范化不保证需求完整，也不涵盖所有可维护性问题。表符合某个范式，不代表时间、事务、查询和演进设计已经合理。

上述属于可检查的理论要求。3NF、BCNF 与依赖保持之间存在取舍；拆分必须能够说明目的和结果。[教材：规范化](https://www.db-book.com/slides-dir/PDF-dir/ch7.pdf)

## 6. 字段字典与完整性约束

每个字段说明名称、含义、类型、范围或长度、单位、精度、空值含义、默认值及修改规则。技术字段也需要有实际用途，不机械加入全部时间戳、状态、版本和软删除字段。

- 使用 `PRIMARY KEY` 表达记录身份，`UNIQUE` 表达相应范围的唯一性，`FOREIGN KEY` 表达必须有效的引用，`CHECK` 和 `NOT NULL` 表达适用的取值规则。
- 数据库能直接表达的重要约束应优先由数据库保护；无法直接表达的跨行、跨表规则必须落实到事务与验证，不能写一句“业务层保证”就结束。
- 不使用笼统的“禁止外键”或“全部级联删除”规则。说明关系删除时应阻止、置空、保留快照还是级联；不使用数据库外键时说明具体替代机制及其验证方式。
- 明确 `NULL`、空字符串、0 和业务状态之间的区别；默认值必须有业务含义，不能只是为了让插入不报错。
- 检查目标数据库对空值唯一性、大小写与排序规则、约束执行的实际行为。逻辑上不同的值不能因错误的排序规则意外相等，反之亦然。
- 多租户数据需要明确标识和引用的作用域，不能只证明目标 ID 存在，却允许跨租户错误关联。

约束的具体语法和行为依赖数据库产品，不能把某一产品的细节当作全部 SQL 实现的统一行为。[PostgreSQL：约束](https://www.postgresql.org/docs/current/ddl-constraints.html)

数值与时间的选择以含义为准：精确计算需要明确精度及舍入；范围决定整数宽度；时间点、日期、持续时长和业务时区分别定义。电话号码或编号即使由数字组成，也不因此适合算术数值类型。[PostgreSQL：数值类型](https://www.postgresql.org/docs/current/datatype-numeric.html)

## 7. 事务、并发与故障恢复

表结构必须放进实际操作里验证。关键操作应写清：读取集合、修改集合、前置条件、提交后必须满足的规则，以及失败状态。

- 先列不可违反的条件，再选择事务边界、条件更新、行锁、版本校验或隔离级别。禁止以“加了事务”代替并发分析。
- 涉及多个记录时，说明哪些修改需要原子提交；锁定范围、访问顺序和重试行为应一致。
- 普通查询后再更新不自动保证并发正确。条件更新需要检查实际影响行数，版本冲突需要明确返回或重试规则。[MySQL：锁定读取](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)
- 重复请求的处理需要稳定的操作标识及唯一性依据；不能靠前端禁用按钮证明幂等。
- 区分事务回滚与外部副作用：数据库回滚不能撤销已经完成的外部调用。需要恢复、重试或补偿时说明其状态与依据。
- 服务中断后不能仅凭内存判断操作是否完成；需要可靠恢复的事实和中间状态必须有明确保存位置。也不能为每个无需恢复的程序步骤机械建表。
- 选择适合所需一致性的隔离级别，并验证数据库的具体实现；处理死锁或可串行化失败时，明确哪些事务可以安全重试。

隔离级别决定哪些并发现象可能发生；事务边界与异常处理同属于设计，不是 DDL 完成后的附属工作。[PostgreSQL：事务隔离](https://www.postgresql.org/docs/current/transaction-iso.html)

## 8. 冗余、索引与物理设计

- 先给出主要查询、过滤、关联、排序、分页方式及预计数据量，再设计索引；用于约束的索引与用于查询性能的索引分别说明。
- 根据执行计划和代表性数据验证索引收益，同时记录写入和存储成本。禁止为所有列建索引，也不根据猜测创建大量近似索引。
- 分区、冷热拆分、分库分表需要容量、维护或访问证据；不能将“以后可能大”直接作为当前引入复杂度的理由。
- 保存汇总或冗余副本时，必须指定权威来源、维护者、更新时机、允许滞后和重建方式。不能让两份同义数据分别接受任意写入。
- JSON、EAV、通用键值表等灵活结构必须说明失去或转移了哪些类型、关系、查询和约束能力，不作为绕过建模的默认方式。

查询性能不能只靠增加结构获得；索引过多或不匹配查询也会形成性能问题。[Microsoft：索引设计指南](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide?view=sql-server-ver17)

## 9. 生命周期、访问边界与演进

- 定义创建、修改、停用、删除、归档和保留期限；没有历史需求时不默认建立全量历史表。
- 软删除不是通用正确答案。采用时必须检查唯一约束、关联、查询过滤、恢复与最终清理；硬删除则检查引用与必须保留的事实。
- 敏感字段明确最小读取范围、日志脱敏和保护方式；模型拆分不能替代权限检查，权限需求也需要说明才可作为物理拆分理由。
- 结构变更采用版本化迁移，说明已有数据的转换与校验。创建新库的基线不能替代升级脚本。
- 破坏性变更需要考虑程序版本兼容、回填过程与恢复方式。不能承诺所有数据或 DDL 都能通过简单逆向脚本恢复。
- 数据库设计可以随已验证需求演进，但每次变更都保留原因、迁移和验证证据；不靠事后比较生产表猜测变更意图。[数据库演进实践](https://www.martinfowler.com/articles/evodb.html)

## 10. 设计说明与审查模板

规模较小的变更可以合并条目，复杂变更按需展开。模板用于暴露推导过程，不用于堆积文档。

### 10.1 整体说明

```text
目标与范围：解决什么已确认需求，不包含什么。
既有结构：已有概念和事实来源，复用／扩展／新增的边界。
数据需求：必须保存的信息、主要读写、生命周期。
规则与假设：已确认规则、设计假设、尚待确定事项。
整体关系：数量、可选性、存在依赖与时间含义。
```

### 10.2 每张新增或调整的表

```text
记录含义：一行表示什么，身份与时间范围是什么。
存在依据：满足哪项需求，为什么合表／拆表／复用。
键与依赖：候选键、主键、业务唯一性、关键函数依赖。
字段与约束：类型、空值、单位、默认值、引用及删除规则。
数据来源：原始事实／历史快照／派生汇总，权威来源在哪里。
生命周期：何时生成、更新、结束或清理，是否需要历史。
```

### 10.3 行为与验证

```text
关键操作：读写哪些记录，提交前后必须成立什么。
并发与失败：重复请求、冲突、中断、恢复如何处理。
物理选择：索引或冗余服务哪些具体查询，有何代价。
演进方式：已有数据如何迁移，如何兼容、验证与恢复。
验证结果：执行过什么，结果如何，哪些尚未执行。
```

审查时至少能回答以下问题：

1. 数据与关系是否完整覆盖已确认需求，是否擅自加入未来功能？
2. 每张表的一行含义、身份和生命周期是否清楚？
3. 拆合是否有依赖、关系或经过说明的物理依据？
4. 所有重要非法状态分别由什么约束或事务规则阻止？
5. 冗余、派生数据与历史快照是否区分，谁是权威来源？
6. 查询、并发、重试、失败恢复和迁移是否有具体检查证据？

未覆盖的方面必须注明实际边界，不能把“DDL 可执行”或“编译通过”报告为设计整体已验证。

## 11. 跨项目复用与持续维护

- 本文维护通用方法。数据库产品版本、命名风格、ID 生成方式、迁移工具、备份步骤和实际验证命令由项目自己的约定补充，不复制进每条通用原则。
- 新项目采用时，在项目约定中指定本文位置及适用范围，并补充技术栈差异；不要因为已有范例是某个数据库就照抄其实现细节。
- 可以随项目复制本规范；复制后独立演进，不宣称会自动同步。需要多项目统一更新时，由使用者明确选择公共文档仓库与引用方式。
- 新经验先记录为案例或候选规则，说明问题、原因、适用前提和反例；经确认后再提升为通用规则。不能把一次修复中的局部结论直接变成所有项目的禁令。
- 修改规则时记录版本、理由和适用范围；有条件的例外写明条件，不静默推翻原规则。
- 来源支持理论和事实，本规范中的工程要求是对资料的整理与选择。发现来源冲突时回到原始定义、目标数据库版本和实际验证，不以文章数量投票。
