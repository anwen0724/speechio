# 文档编写规则

本文规定项目文档在编写、修改和检查时应遵守的通用要求。各类文档的用途、内容范围和模板见对应说明，入口为[如何使用项目文档体系](../usage-guide.md)。

编写或维护文档时，读取本文及对应类型的说明。普通代码开发不要求重复阅读本文。以下要求按文档涉及的内容适用，不要求每份文档都包含数据、接口、状态或验收章节。

## 内容依据

- 区分已确认要求、观察到的事实、建议和待决策问题。建议和待决策问题不应写成有效约定；正式设计正文只记录已确认的设计。
- 描述当前实现时，应依据代码、配置或实际验证。已有设计不能证明实现已经完成，现有代码也不能自动成为产品要求。
- 未核实的内容应说明尚未核实，不应推测为确定结论。讨论中尚未确认的问题不写入正式设计，可记录在讨论资料或 Status 的待决策项中。
- 引用要求、结论或验证结果时，应注明能够定位的来源。来源可以是文档章节、代码位置、提交或验证记录，不必为每句普通说明添加引用。
- 资料冲突时，应先判断各自描述的是要求、现状还是历史，再确定哪一处需要修改。不应为了让文档一致而掩盖实现缺口。
- 示例应明确标注为示例。示例中的参数、技术选择和结果不构成项目要求，也不应被当作实测证据。

## 编写顺序

以下顺序适用于新建或重新组织文档。局部修改只需检查受影响的部分。

1. 明确文档的用途、范围，以及读者需要解决的问题。
2. 核对已有资料，区分已确认约定、实现事实和待决策事项。
3. 按对应类型的说明组织内容，并引用所依据的有效资料。
4. 检查内容依据、表达清晰度，以及文档内部和文档之间的一致性。

后续资料改变原有判断时，应更新受影响的内容。不应为了填满模板而编造内容。

## 描述要求

### 文字与术语

- 同一概念使用同一名称。新术语应在首次使用时说明含义，不用多个近义名称交替表示同一对象。
- 同一术语不应在同一文档中表示不同概念；确有不同含义时，应明确区分。
- 优先沿用项目已确认的术语。文件名、接口名、字段名和命令应与实际标识一致，并使用代码格式，不翻译标识或改变大小写。
- 描述行为时，应说明谁在什么条件下执行什么动作，以及产生什么结果。主体改变时应重新写明主体，避免含糊指代。
- 一句话围绕一个意思展开。描述有条件的操作或行为规则时，先说明条件，再说明动作。复杂的并列内容可拆为列表或表格。
- 用“应／不应”表达要求，用“宜／不宜”表达推荐，用“可／不必”表达允许或不要求。描述能力时使用“能／不能”，不将能力描述当作约束。
- “必要时”“合理”“重复”“及时”等词如果影响执行判断，应同时说明条件或含义，不让执行者自行猜测。

以下示例只展示表达方式，不构成项目要求。涉及主体、条件或要求强度的改写，应以已经确认的含义为依据；原意不明确时，先确认，不通过润色自行决定。

| 要求 | 原句 | 改写 |
| --- | --- | --- |
| 同一概念同名 | 服务启动时加载配置……重启后重新读取设置……修改参数后需要重新初始化。 | 服务启动时读取配置。修改配置后，重新启动服务。 |
| 主体明确 | 提交后自动跑测试，失败就打回。 | 开发者提交代码后，CI 自动运行测试；测试失败时，CI 拒绝合并。 |
| 指代明确 | `Client` 把请求交给 `Pool`，它负责重试。 | `Client` 把请求交给 `Pool`。`Pool` 负责重试。 |
| 条件前置 | 运行 Y（如果 X）。 | 如果 X，运行 Y。 |
| 判断条件明确 | 在适当的时候清理缓存。 | 配置文件改动后，清掉配置缓存。 |
| 要求强度明确 | 上线前最好跑一下回归测试。 | 上线前应运行回归测试。 |

第一行假定“配置”“设置”“参数”指同一份配置，“启动”“初始化”指同一动作。最后一行适用于回归测试已被确认为要求的情况，不应将推荐擅自改为要求。

一词一义的示例：“构建”定为“类型检查加打包”，那么只做打包的那一步就写“打包”，不写“构建”。这是示例中的术语约定，不代表所有项目对“构建”的定义。

代码格式的示例：`parseConfig`、`--dry-run`、`HTTP_PROXY`。

### 按内容适用的要求

以下要求仅在文档承担对应内容时适用，不要求每份文档都描述功能、数据、接口或验收。

- 描述功能行为时，应说明正常结果、关键边界和主要失败结果。涉及重复执行、中断或部分完成时，应说明已经发生的变化以及后续结果。
- 描述数据和状态时，应说明含义、归属和变化。字段、默认值、状态转换、持久化和迁移等细节，只在理解或实现契约需要时展开。
- 描述接口时，应说明调用方、输入、输出和失败结果。依赖外部能力时，应说明依赖提供的结果及失败对本功能的影响。
- 定义验收标准时，应包含可判断的条件和结果，不只写“功能正常”或“符合预期”。验收标准应对应已确认要求，不应自行新增行为。
- 定义跨模块或跨 Spec 验收时，应区分本份能够证明的结果与集成后才能证明的结果，并明确联合验证的承担方。不应把本份核心目标移到后续验证中，再宣布本份完成。
- 记录验证结果时，应说明实际验证范围。自动化、模拟环境和真实使用的结果不应相互替代；未验证的部分应保留说明。

### 图表

只有当图表比文字更清楚地表达结构、流程或比较时才使用，不要求每份文档都配图。

- 图应说明对象和范围；连线应明确表示依赖、调用、数据传递或状态转换中的哪一种关系。
- 图中的名称应与正文一致，不用一个未说明的箭头混合表达多种关系。
- 表格适合比较相同维度，不应用表格压缩必须连贯说明的条件和因果。
- 图表与正文可以相互补充，但不应定义不同的规则。关系变化时，应同步修改受影响的图表和文字。

## 修改要求

- 修改前，应核对目标文件及其当前内容，保留仍有效的要求、限制、例外和验证边界。
- 改变已确认的目标、范围或行为时，应明确指出变化；尚未获得确认的取舍不应借文字整理直接写入。已经明确授权的修改不必重复确认。
- 修改措辞或组织结构时，不应改变原有要求的强度，也不应把有条件成立的结论改成无条件承诺。
- 规则应在负责它的文档中修改，其他文档更新概述或引用。不要在多个位置各维护一套完整定义。
- 局部修改后，应检查受影响的目标、规则、数据、接口、流程和验收是否仍然一致。不应只追加一个补丁段落，让旧结论继续留在正文中。
- 移动、替代或删除文档时，应核对引用并同步入口。需要追溯的历史内容按维护约定保留，并明确不再生效。

## 完成检查

完成编写或修改后，检查以下项目。只检查本文档涉及的内容，不为无关项目补写章节。

- 文档的目标、范围和内容属于同一职责，没有混入其他文档的完整任务。
- 要求、事实、建议和示例能够区分，来源足以支撑结论。
- 条件、主体、动作和结果明确，术语和指代没有歧义。
- 文档中的结论相互一致，与引用的有效约定不冲突；涉及规则、数据、接口、流程或验收时，对应内容也应一致。
- 定义功能契约时，关键边界和失败结果已说明，没有把影响契约的取舍留给实施者猜测。
- 已完成与待完成、已验证与未验证明确区分。
- 图表与正文一致，链接有效，被替代的内容不再作为当前依据。
- 没有为了套用模板增加无依据的内容，也没有重复维护其他文档的完整约定。

检查结论应说明检查范围、发现的问题和未解决事项。格式或脚本检查通过不能代替语义审查；文档审查通过也不能证明软件已经实现或验收通过。
